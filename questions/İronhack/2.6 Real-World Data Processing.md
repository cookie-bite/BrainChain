# Real-World Data

## Introduction

In a classroom, datasets arrive clean: every column has a type, every row is complete, and the labels are balanced. In the real world, nothing works that way. Data has missing values for reasons that are themselves informative. Categories evolve — new brands appear daily, old product types vanish. Classes are wildly imbalanced — 99.99% of transactions are legitimate, and the 0.01% that are fraudulent are exactly the ones you need to catch. And the most dangerous problems are the ones you cannot see: information from the future leaking into your training data, giving your model an unfair advantage during evaluation that evaporates the moment it hits production.

This lesson is about developing the judgment to look at a real dataset and know what is broken, what is dangerous, and what to do about it. We will work through missing values, categorical data challenges, class imbalance, data augmentation, and data leakage — each with concrete Python code so you can see the mechanics, not just the concepts.

## Missing Values: Not All Absences Are Equal

One of the first things you notice when working with production data is that values are missing. But here is the critical insight that many practitioners miss: the reason a value is missing can be just as informative as the value itself. There are three types of missing data, and confusing them leads to bad decisions.

### 1. Missing Not at Random (MNAR)

The value is missing because of the true value itself. High earners are less likely to disclose their income on a survey. Patients with serious conditions are less likely to complete follow-up questionnaires. The missingness tells you something about what the value would have been.

### 2. Missing at Random (MAR)

The value is missing because of another observed variable, not the value itself. In a survey, respondents of gender A might systematically skip the age question — not because of their age, but because people of gender A in this particular survey do not like disclosing it. Once you control for gender, the age missingness has no pattern.

### 3. Missing Completely at Random (MCAR)

There is no pattern at all. People just forgot to fill in a field sometimes. This type of missing data is rare in practice. There are usually reasons why values are missing, and you should investigate.

Let's see how these types play out in code:


```
import numpy as np
import pandas as pd

np.random.seed(42)
n = 1000

# Simulated survey data
income = np.random.lognormal(mean=10.8, sigma=0.7, size=n)  # Right-skewed
age = np.random.randint(18, 75, size=n)
gender = np.random.choice(["A", "B"], size=n, p=[0.4, 0.6])

df = pd.DataFrame({"age": age, "gender": gender, "income": income})

# MNAR: high earners are less likely to report income
prob_missing_income = np.where(income > np.percentile(income, 75), 0.6, 0.1)
df.loc[np.random.random(n) < prob_missing_income, "income"] = np.nan

# MAR: gender A respondents are less likely to report age
prob_missing_age = np.where(gender == "A", 0.5, 0.05)
df.loc[np.random.random(n) < prob_missing_age, "age"] = np.nan

# MCAR: job field is randomly missing
df["job"] = np.random.choice(["engineer", "teacher", "doctor", "student"], n)
df.loc[np.random.random(n) < 0.1, "job"] = np.nan

print("Missing values:")
print(df.isnull().sum())
print(f"\nMedian income (all): ${np.nanmedian(income):,.0f}")
print(f"Median income (reported): ${df['income'].median():,.0f}")
print(f"  --> Reported income is biased LOW because high earners hide theirs (MNAR)")

print(f"\nAge missing rate for gender A: {df.loc[df['gender']=='A', 'age'].isnull().mean():.1%}")
print(f"Age missing rate for gender B: {df.loc[df['gender']=='B', 'age'].isnull().mean():.1%}")
print(f"  --> Dropping rows with missing age removes most gender A respondents (MAR)")
```

### Deletion: Easy but Dangerous

The simplest approach is to remove rows or columns with missing values. Column deletion removes an entire feature if too many values are missing. Row deletion removes individual samples. Both are tempting because they are easy, but both can introduce serious problems.

Row deletion only works safely when data is MCAR and the number of missing rows is tiny (less than 0.1% of data). If data is MAR, dropping rows creates biased data — in our example, removing rows with missing age eliminates most gender A respondents. If data is MNAR, dropping rows removes the very signal that matters — the fact that income is missing is itself predictive of high income.


```
# Demonstrating the danger of naive row deletion
df_complete = df.dropna()

print(f"Original: {len(df)} rows")
print(f"After dropna: {len(df_complete)} rows ({len(df_complete)/len(df):.0%} retained)")
print(f"\nGender distribution (original): {df['gender'].value_counts(normalize=True).to_dict()}")
print(f"Gender distribution (after drop): {df_complete['gender'].value_counts(normalize=True).to_dict()}")
print("  --> Gender A is severely underrepresented after dropping rows with missing age")
```

### Imputation: Better but Not Free

Imputation means filling missing values with estimated values. Common strategies include filling with the mean, median, mode, or a domain-specific default. But imputation has its own traps:


```
# Filling missing income with mean hides the MNAR signal
mean_income = df["income"].mean()
df_imputed = df.copy()
df_imputed["income"] = df_imputed["income"].fillna(mean_income)

# Better: add a flag column that captures the missingness signal
df_imputed["income_was_missing"] = df["income"].isnull().astype(int)

print(f"Income mean (original): ${df['income'].mean():,.0f}")
print(f"Income mean (after imputation): ${df_imputed['income'].mean():,.0f}")
print(f"Income-missing flag captures the MNAR signal: {df_imputed['income_was_missing'].sum()} flagged rows")
```

> **The Sentinel Rule:** Avoid filling missing values with plausible real values. Filling missing "number of children" with 0 is dangerous because 0 is a valid value. You cannot distinguish between someone who has no children and someone whose data is missing. Use sentinel values (like -1) or separate indicator columns instead.

## Common Data Cleaning Operations

Before any modeling, real datasets need cleaning. The operations below come up in almost every project.

### Feature Scaling

Features on different scales cause problems. If age ranges from 20 to 40 and income ranges from 10,000 to 150,000, a model will see 150,000 as "bigger" than 40 and may give it more weight — regardless of which feature is actually more predictive.


```
from sklearn.preprocessing import StandardScaler, MinMaxScaler

raw = pd.DataFrame({
    "age": [25, 32, 45, 28, 55],
    "income": [35000, 72000, 120000, 48000, 95000],
    "years_experience": [2, 8, 20, 4, 30],
})

# Min-max scaling: squeeze each feature to [0, 1]
scaler_mm = MinMaxScaler()
scaled_mm = pd.DataFrame(scaler_mm.fit_transform(raw), columns=raw.columns)

# Standardization: zero mean, unit variance
scaler_std = StandardScaler()
scaled_std = pd.DataFrame(scaler_std.fit_transform(raw), columns=raw.columns)

print("Original:\n", raw)
print("\nMin-Max scaled:\n", scaled_mm.round(3))
print("\nStandardized:\n", scaled_std.round(3))
```

For skewed features (like income, which tends to follow a lognormal distribution), log transformation can reduce skewness and help models learn more effectively:


```
df_log = raw.copy()
df_log["log_income"] = np.log1p(raw["income"])
print(f"Income range: {raw['income'].min()} – {raw['income'].max()}")
print(f"Log-income range: {df_log['log_income'].min():.2f} – {df_log['log_income'].max():.2f}")
```

### Encoding Categorical Features

Static categories (like age brackets or product types that never change) are simple: assign each category an integer and move on. But in production, categories evolve. New brands appear on Amazon daily. New user accounts are created every minute. A model trained on yesterday's categories will crash when it encounters a brand it has never seen.

The common quick fix is to create an `UNKNOWN` bucket for unseen categories. This works until you realize your model treats all unknown brands identically — new luxury brands, sketchy knockoffs, and established names all get the same prediction.

A more robust approach is the **hashing trick**: use a hash function to map each category to a fixed-size index space. New categories automatically get a hash value without any code changes. Collisions happen, but research at Booking.com showed that even a 50% collision rate causes less than 0.5% performance loss.


```
# One-hot encoding for small, static categories
categories = pd.DataFrame({"color": ["red", "blue", "green", "red", "blue"]})
one_hot = pd.get_dummies(categories, prefix="color")
print("One-hot encoding:\n", one_hot)

# Hashing trick for large, evolving categories
import hashlib

def hash_category(value, n_buckets=1024):
    """Hash a category string into a fixed number of buckets."""
    h = int(hashlib.md5(value.encode()).hexdigest(), 16)
    return h % n_buckets

brands = ["Nike", "Adidas", "NewBrand2026", "UnknownStartup", "Nike"]
hashed = [hash_category(b) for b in brands]
print(f"\nHashed brand indices (1024 buckets): {dict(zip(brands, hashed))}")
```

## Class Imbalance: When Rare Events Matter Most

Class imbalance is the norm in real-world ML. Fraud detection datasets have 99.99% legitimate transactions. Cancer screening data has overwhelmingly normal cases. Resume screening rejects 98% of applicants at the first stage. In every case, the rare class is the one you care about most.

### Why Imbalance Makes Learning Hard

Class imbalance causes three problems. First, there is simply insufficient signal for the minority class. Second, the model can get stuck in a trivial solution: always predicting the majority class gives 99.99% accuracy on fraud detection, even though the model has learned nothing useful. Third, the cost of errors is asymmetric: missing a cancerous X-ray is far more dangerous than flagging a normal one.


```
# Demonstrating the accuracy trap with imbalanced data
np.random.seed(42)
n_samples = 10000

# 99.5% negative, 0.5% positive (fraud)
labels = np.random.choice([0, 1], n_samples, p=[0.995, 0.005])

# A "model" that always predicts majority class
always_negative = np.zeros(n_samples)
accuracy = (always_negative == labels).mean()
print(f"Always predict 'not fraud': accuracy = {accuracy:.3%}")
print(f"  But it catches {(always_negative[labels==1] == 1).sum()}/{(labels==1).sum()} actual fraud cases")
```

### Choosing the Right Metrics

Overall accuracy is misleading for imbalanced tasks. Use metrics that focus on the class you care about:


```
from sklearn.metrics import precision_score, recall_score, f1_score, confusion_matrix

# Two hypothetical models with the same accuracy but different behavior
y_true = np.array([1]*100 + [0]*900)

# Model A: conservative — catches 10/100 fraud cases
y_pred_a = np.array([1]*10 + [0]*90 + [0]*890 + [1]*10)

# Model B: aggressive — catches 90/100 fraud cases
y_pred_b = np.array([1]*90 + [0]*10 + [0]*810 + [1]*90)

for name, y_pred in [("Model A", y_pred_a), ("Model B", y_pred_b)]:
    acc = (y_pred == y_true).mean()
    prec = precision_score(y_true, y_pred)
    rec = recall_score(y_true, y_pred)
    f1 = f1_score(y_true, y_pred)
    print(f"{name}: accuracy={acc:.3f}  precision={prec:.3f}  recall={rec:.3f}  F1={f1:.3f}")

print("\nBoth models have the same accuracy, but Model B catches 9x more fraud.")
print("F1, precision, and recall reveal the real difference.")
```

### Data-Level Methods: Resampling

Resampling techniques modify the training data distribution to make it less imbalanced. The two basic approaches are oversampling (adding copies of the minority class) and undersampling (removing examples of the majority class).


```
from collections import Counter

# Simulated imbalanced dataset
np.random.seed(42)
X = np.random.randn(1000, 5)
y = np.array([0]*950 + [1]*50)
print(f"Original: {Counter(y)}")

# Random oversampling: duplicate minority class
minority_indices = np.where(y == 1)[0]
oversampled_indices = np.random.choice(minority_indices, size=950-50, replace=True)
X_over = np.vstack([X, X[oversampled_indices]])
y_over = np.concatenate([y, y[oversampled_indices]])
print(f"After oversampling: {Counter(y_over)}")

# Random undersampling: remove majority class examples
majority_indices = np.where(y == 0)[0]
undersampled_indices = np.random.choice(majority_indices, size=50, replace=False)
X_under = np.vstack([X[undersampled_indices], X[minority_indices]])
y_under = np.concatenate([y[undersampled_indices], y[minority_indices]])
print(f"After undersampling: {Counter(y_under)}")
```

Simple oversampling risks overfitting because the model sees exact copies of minority examples. Simple undersampling risks losing information from discarded majority examples. Advanced alternatives include:

* **SMOTE (Synthetic Minority Oversampling Technique):** Creates new minority samples by interpolating between existing ones rather than duplicating them. It works well for low-dimensional data but struggles in high-dimensional feature spaces.
* **Tomek links:** Identify pairs of opposite-class samples that are close together and remove the majority-class member of each pair to clean the decision boundary.

> **The Resampling Golden Rule:** Never evaluate on resampled data. Resampling changes the distribution. If you evaluate on the resampled distribution instead of the original one, your metrics will overestimate performance. Always resample only the training set; keep validation and test sets at their natural distribution.

### Algorithm-Level Methods: Loss Function Adjustments

Instead of changing the data, you can change how the model learns. The idea is to make mistakes on the minority class more expensive.

* **Cost-sensitive learning:** Uses a cost matrix that assigns different penalties for different types of misclassification.
* **Class-balanced loss:** Weights each class inversely proportional to its frequency. The rarer the class, the higher the weight in the loss function.
* **Focal loss:** Reduces the loss for well-classified examples and increases it for hard examples, focusing the model on what it gets wrong.


```
# Class-balanced weights
class_counts = Counter(y)
total = sum(class_counts.values())
weights = {cls: total / count for cls, count in class_counts.items()}
print(f"Class weights: {weights}")
print(f"  --> Minority class gets {weights[1]/weights[0]:.0f}x the weight of majority class")
```

## Data Augmentation: Generating More from Less

Data augmentation increases the effective size of your training data by creating modified versions of existing examples. It is proven useful even for large datasets by making models more robust to noise and structural fluctuations.

### Label-Preserving Transformations

* **For images:** You can crop, flip, rotate, invert, or erase parts of the image. A rotated dog is still a dog. Modern frameworks (PyTorch, TensorFlow) generate these on the CPU on the fly while the GPU trains on the previous batch.
* **For text:** You can replace words with synonyms using dictionaries or finding close neighbors in an embedding space. `"I'm so happy to see you"` can become `"I'm so glad to see you"`.

### Perturbation: Adding Noise Strategically

Neural networks are surprisingly sensitive to small noise. Adding noise to training data forces the model to learn more robust, stable representations.

* **Adversarial augmentation:** Finds the minimum noise needed to fool the model and adds those adversarial examples to the training data to strengthen its weakest spots.
* **Token Masking:** In NLP, frameworks like BERT randomly replace 1.5% of tokens with random words during training, which measurably improves performance.

### Data Synthesis

When collecting real data is too expensive, synthetic data can bridge the gap. For NLP tasks, templates provide a cheap way to bootstrap training data: `"Find me a [CUISINE] restaurant within [NUMBER] miles of [LOCATION]"` generates thousands of variants.

Another approach is **mixup**, which blends two images and their labels — a 70/30 blend of a dog image (label 0) and a cat image (label 1) gets label 0.3. This improves generalization and stabilizes training boundaries.

## Data Leakage: The Silent Killer

Data leakage occurs when information that would not be available at prediction time leaks into your training data. It is the most dangerous problem in ML engineering because it makes your model look great during evaluation and fail catastrophically in production.

### Common Causes

**1. Splitting time-correlated data randomly:** In production, you always predict the future from the past. If you randomly shuffle time-series data before splitting, future information leaks into your training set.


```
# Demonstrating temporal leakage
np.random.seed(42)
dates = pd.date_range("2024-01-01", periods=100, freq="D")

# Simulated feature that drifts over time
feature = np.cumsum(np.random.randn(100)) + np.arange(100) * 0.1
target = (feature > np.median(feature)).astype(int)

df_time = pd.DataFrame({"date": dates, "feature": feature, "target": target})

# WRONG: random split
train_rand, test_rand = train_test_split(df_time, test_size=0.2, random_state=42)
print("Random split:")
print(f"  Train dates: {train_rand['date'].min().date()} to {train_rand['date'].max().date()}")
print(f"  Test dates:  {test_rand['date'].min().date()} to {test_rand['date'].max().date()}")
print(f"  --> Train and test dates are INTERLEAVED — future leaks into past!\n")

# RIGHT: temporal split
split_date = dates[80]
train_time = df_time[df_time["date"] < split_date]
test_time = df_time[df_time["date"] >= split_date]
print("Temporal split:")
print(f"  Train dates: {train_time['date'].min().date()} to {train_time['date'].max().date()}")
print(f"  Test dates:  {test_time['date'].min().date()} to {test_time['date'].max().date()}")
print(f"  --> All test data comes AFTER all train data — no future leakage")
```

**2. Scaling before splitting:** Feature scaling requires global statistics (mean, variance). If you compute these on the full dataset before splitting, information from the test set leaks into training. Always split first, then compute statistics only on the training set:


```
from sklearn.preprocessing import StandardScaler

# WRONG: scale before split
scaler_wrong = StandardScaler()
df_time["feature_scaled_wrong"] = scaler_wrong.fit_transform(df_time[["feature"]])

# RIGHT: scale after split, using only training statistics
scaler_right = StandardScaler()
train_time = train_time.copy()
test_time = test_time.copy()

train_time["feature_scaled"] = scaler_right.fit_transform(train_time[["feature"]])
test_time["feature_scaled"] = scaler_right.transform(test_time[["feature"]])  # transform, not fit_transform!

print("Scaling after split: train stats used for both train and test transforms")
print(f"  Scaler mean (from train only): {scaler_right.mean_[0]:.3f}")
```

**3. Imputing missing values with global statistics:** If you compute the median of a feature across the full dataset and use it to fill missing values, test-set distribution leaks into training.

**4. Data duplication and Group leakage:** If duplicate rows span across splits, the model memorizes them. Similarly, if multiple medical scans of the same patient end up in different splits, the model effectively sees the test target via group traits. Keep data from the same entity (patient, user, session) grouped within the same split.

### Detecting Data Leakage

There is no single programmatic test for data leakage. Instead, build a habit of checking:

* **Suspiciously high correlation:** If a feature predicts the label almost perfectly, investigate how it was generated.
* **Ablation studies:** If removing a single feature causes an extreme performance drop, that feature may contain leaked info.
* **Generation process review:** Check if the data implies structural rules (e.g., if a hospital assigns a specific scanner type only to high-risk patients, the model will learn to classify the machine instead of the disease condition).


```
# Simple leakage detection: check feature-target correlation
np.random.seed(42)
n = 1000
legitimate_feature = np.random.randn(n)
target = (legitimate_feature + np.random.randn(n) * 0.5 > 0).astype(int)

# Suppose someone accidentally includes a derived-from-target feature
leaked_feature = target + np.random.randn(n) * 0.01

features = pd.DataFrame({
    "legitimate": legitimate_feature,
    "leaked": leaked_feature,
    "target": target,
})

correlations = features.corr()["target"].drop("target").abs().sort_values(ascending=False)
print("Feature-target correlations (absolute):")
print(correlations)
print(f"\n'leaked' has suspiciously high correlation ({correlations['leaked']:.4f}) — investigate!")
```

## Summary

* **Missing values belong to specific regimes (MNAR, MAR, MCAR).** Deletion introduces extreme bias, while naive imputation masks structural patterns. Flag indicators ensure you preserve the missingness signature.
* **Categorical pipelines must handle infinite variance.** Static fields can use standard encoders, but dynamically evolving strings are best processed via the hashing trick to map terms safely onto a fixed vector space.
* **Class imbalance requires metric discipline.** Drop overall accuracy in favor of precision, recall, and F1-scores. Resampling tactics must be strictly constrained to training boundaries, never touching evaluation datasets.
* **Data leakage is an architectural bug.** It emerges from loose data validation, scaling datasets globally before performing data splitting, or failing to group identity entities across production train and test layers. Always audit highly correlated features explicitly.
