# Python, IPython, and Jupyter

## Introduction

When you do data work in Python, you are constantly moving between ideas and evidence. You sketch a question, you load a dataset, you try a few transformations, you visualize a result, and then you refine the question. This lesson builds the environment and habits that make that workflow fast, reliable, and expressive. We will focus on the interactive Python interpreter, the enhanced features of IPython, and the notebook environment that ties code, narrative, and output together. Along the way, you will build clear mental models for how Python executes code, how the interactive shell helps you think, and how a notebook can become a durable, reproducible record of analysis.

The goal is not just to “run Python.” The goal is to understand why the tools are built the way they are and how to make them serve your reasoning process. If you treat the environment as part of your analytical method, you will write clearer code, catch errors earlier, and move from raw data to insight more confidently.

## The Python Interpreter as a Thinking Tool

Python code is executed by an interpreter, which reads your program and runs it line by line. In an interactive session, that interpreter becomes a conversation. You type an expression, the interpreter evaluates it, and it immediately shows the result. This feedback loop is fundamental to data analysis because many decisions depend on what you see in the data right now.

Consider a simple interactive session:


```
2 + 2
```

The interpreter returns 4 because it evaluates the expression, performs integer addition, and prints the result. This seems trivial, but the mental model matters. In Python, many things are expressions that produce values, and understanding that lets you build complex transformations out of small, testable pieces. When you call a function or index into a structure, you are still evaluating an expression that returns a value, even if that value is a complex object.

If you assign a value to a name, the interpreter binds that name in the current namespace:


```
value = (2 + 2) * 3
value
```

The first line computes $(2 + 2) \times 3$, which is 12, and then stores the result in the name value. When you evaluate value, the interpreter looks it up and returns 12. This two-step pattern of building a value and binding it to a name is the core of readable analysis code. You build computations out of expressions and then give the result a meaningful name.

The interpreter also keeps track of a working directory, which influences how Python finds files you read and write. If you are experimenting interactively, you want to be aware of where your session “lives” so that file paths make sense. You can check it like this:


```
import os
os.getcwd()
```

The os module is part of the standard library. Calling os.getcwd() returns a string with the current working directory. This is a small example of how Python gives you direct access to the environment in which your analysis runs.

## Running Python Code: Files, Scripts, and the REPL

Interactive work is great for exploration, but analysis often needs to be saved and repeated. That is where scripts and modules come in. A Python script is simply a file ending in .py that contains statements to execute. When you run a script, Python executes it top to bottom in a fresh namespace.

Suppose you save the following code in a file called simple_stats.py:


```
import numpy as np 
data = [1.5, 2.0, 2.5, 3.0, 2.0]
mean = np.mean(data)
std = np.std(data) 

print("Mean:", mean)
print("Std:", std)
```

When this script runs, Python imports NumPy, creates a list of numbers, computes the mean and standard deviation, and prints them. This is how you turn interactive experiments into repeatable results. You can run the script from a terminal, or you can execute it inside an interactive environment. The key idea is that scripts are for reproducibility, while the interactive interpreter is for exploration. In practice, analysts move between them constantly, validating an idea in the interpreter and then capturing it in a script or notebook.

The interactive interpreter is often called the **REPL**, which stands for Read–Eval–Print Loop. It reads your input, evaluates it, prints the result, and loops back for more input. This cycle is why interactive analysis feels quick and responsive. You are effectively doing live programming with immediate feedback, which is perfectly aligned with exploratory data analysis.

## IPython: An Enhanced Interactive Shell

IPython is an interactive shell built for scientific and data work. It extends the basic Python interpreter with features that make exploration faster and safer. The first time you use IPython, you will notice that it provides richer error messages, better introspection, and convenient shortcuts.

A practical example of introspection is being able to see what a function expects. In plain Python, you might need to consult documentation separately. In IPython, you can inspect objects and functions interactively, which is crucial when you are working with unfamiliar APIs or quickly exploring a dataset.

Suppose you have a Pandas Series and you want to know its available methods:


```
import pandas as pd 
series = pd.Series([10, 20, 30], name="numbers")
series
```

In IPython, you can type series. and press Tab to see attribute and method names. This is more than a convenience. It encourages exploratory programming, where you discover and use functionality by interacting with objects directly. This is especially helpful in data analysis, where you often need to inspect and manipulate structures without knowing every method by heart.

IPython also keeps a history of your commands, and you can search that history. This matters in a long exploratory session where you want to reuse or tweak a transformation you wrote earlier. A reliable history is a safety net for exploratory work.

## Magic Commands and Shell Integration

IPython adds special “magic” commands that start with % or %%. These are not normal Python syntax. They are commands interpreted by IPython itself, and they provide convenient access to features such as timing code, running scripts, and interacting with the system shell.

If you have a script file, you can run it directly inside IPython:


```
%run simple_stats.py
```

This executes the script in your current session, which means variables defined in the script can become available to you after it runs. This is a powerful pattern: you can place reusable logic in a script, run it in IPython, and then inspect the resulting variables interactively. It helps blend reproducibility with exploration.

Another example is timing. Suppose you want to know how long a computation takes:


```
import numpy as np 
data = np.random.randn(1_000_000)
%time result = data.sum()
```

The %time magic measures the execution time of a single line. IPython executes the line, computes the sum, and reports how long it took. This is invaluable when you want to compare approaches, such as using a loop versus a vectorized operation. It encourages a performance-aware mindset without forcing you into premature optimization.

IPython also lets you call system shell commands using !. This is useful when you need to quickly list files, check the contents of a directory, or run a data download script:


```
!ls
```

The command runs in your system shell, and the output is captured in the notebook or terminal. This gives you a smooth transition between analysis code and the surrounding filesystem context, which is often necessary when managing data files.

## Jupyter Notebook: A Living Analysis Document

The Jupyter Notebook takes the interactive shell and wraps it into a document that mixes code, text, and output. A notebook is not just a place to run code; it is a narrative of your analysis. When you write a notebook well, another analyst can understand the sequence of your reasoning, see the transformations applied to data, and reproduce your results.

In a notebook, code is organized into cells. When you run a cell, its output appears directly below it. This tight coupling between code and output supports a step-by-step analytical narrative. It also makes it easy to insert explanations between computations, which is essential when your analysis will be read by others or revisited later.

Imagine you are examining a dataset and want to explain what you are doing:


```
import pandas as pd 
df = pd.DataFrame({
    "city": ["Seoul", "Berlin", "Nairobi", "Toronto"],
    "temperature_c": [26.5, 18.2, 22.1, 16.7],
    "humidity": [0.60, 0.65, 0.58, 0.70],
}) 
df
```

This code creates a small DataFrame and prints it. In a notebook, you can surround this cell with text that explains why you chose these columns, what the units mean, and what questions you plan to answer. The notebook becomes a structured narrative, not just a collection of computations.

### Notebooks and Reproducibility

Reproducibility is a central concern in data analysis. A notebook helps, but only if it is run in a clean, consistent way. It is easy to execute cells out of order or to reuse variables in ways that are no longer visible. The mental model you need is that each cell is a step in a process, and the notebook as a whole is a script with optional branches. To keep it reproducible, you should run cells in order from top to bottom when finalizing an analysis.

Python’s execution model explains why this matters. The interpreter maintains a single namespace for the session. When you execute a cell, it modifies that namespace, and the changes persist. If you define a variable in a later cell and then re-run an earlier cell, you can create a state that never occurs in a clean run. That is why it is important to design notebooks with a clear top-to-bottom flow and to re-run them from the beginning before sharing results.

Consider this example:


```
import numpy as np 
values = np.array([1.0, 2.0, 3.0])
values = values * 10
values
```

If you run these lines in order, you see the scaled array. But if you skip the first line and re-run only the scaling line, the state might not be what you expect. The notebook feels like an interactive document, but underneath it is still the same interpreter with a persistent namespace. Treating the notebook as a living script gives you the best of both worlds: interactivity during exploration and reproducibility when you finalize.

## The Python Language: Expressions, Statements, and Blocks

To use the interpreter effectively, you need to understand how Python distinguishes between expressions and statements. An expression produces a value. A statement performs an action, like binding a name or controlling flow. This distinction helps explain why some lines produce output and others do not.

For example, 3 * 7 is an expression that produces 21, while x = 3 * 7 is a statement that binds the result to x. In an interactive session, expressions are printed automatically, while statements usually produce no output. This behavior is consistent and helps you reason about what you will see.

Python also uses indentation to define blocks of code. This is not just a style preference; it is part of the language. A block begins after a line ending with a colon and continues until the indentation level decreases. This is the mechanism that defines functions, loops, and conditionals.

Here is a basic conditional:


```
x = 5 
if x > 3:
    message = "x is greater than 3"
else:
    message = "x is 3 or less" 
message
```

The if and else lines end with colons, and the indented blocks below them define what to do in each case. The interpreter uses indentation to know where each block starts and ends. This makes Python code visually consistent and easy to scan, which is particularly important in data analysis where you might combine logic, data transformations, and visualization in the same notebook.

## Objects, Types, and Names

Python is an object-oriented language, which means that every value is an object. Objects have a type, and that type determines the operations that are available. When you bind a name to a value, you are not copying the value; you are creating a reference to the object. This matters when you work with mutable data structures and when you share objects across variables.

You can inspect the type of an object using type():


```
temperature = 22.5
type(temperature)
```

The interpreter returns <class 'float'>. This tells you that the object is a floating-point number. If you later assign temperature = "22.5", the name now refers to a string object. This dynamic typing is flexible, but it also means you need to be deliberate about what kinds of values you use in calculations. In data analysis, errors often come from mixing types unintentionally.

You can also convert types explicitly:


```
raw = "3.14159"
value = float(raw)
value
```

Here, float(raw) converts the string to a numeric value. This is a common step when loading data from files, where numeric values may arrive as strings. Understanding how and when to convert types helps you ensure correctness before you proceed to analysis.

## Function Calls and Introspection

Functions are objects in Python, and calling a function is just another expression. The interpreter evaluates the function object, evaluates the arguments, and then executes the function body. In data analysis, functions let you encapsulate transformations and reuse them across datasets.

Here is a simple function for standardizing values:


```
import numpy as np 
def standardize(values):
    values = np.asarray(values)
    return (values - values.mean()) / values.std() 

standardize([2, 4, 6, 8, 10])
```

The function converts the input to a NumPy array, computes the mean and standard deviation, and returns standardized values. This works because NumPy arrays support vectorized operations, so subtracting values.mean() applies elementwise. The result is a new array with zero mean and unit variance. This pattern is common in preprocessing for analytics and machine learning, where standardized inputs are often more stable for models.

In an interactive environment, you can inspect the function’s signature and documentation. IPython makes this easier by letting you access help and source code directly. This is practical when you want to understand how a function behaves, what arguments it expects, or whether it returns a copy or a view. In analysis work, that kind of understanding prevents subtle bugs and improves your ability to reason about results.

## Errors and Debugging in Interactive Work

Errors are not just obstacles; they are signals. The Python interpreter raises exceptions when something goes wrong, and IPython shows detailed tracebacks that tell you where the error occurred. Learning to read these tracebacks is essential for efficient problem solving.

Consider this error:


```
values = [1, 2, 3]
values + 10
```

Python raises a TypeError because you cannot add an integer to a list. The error message explains the mismatch. In data analysis, type errors often signal that a value is not in the format you expect. The fix here is to use a NumPy array, which supports elementwise addition:


```
import numpy as np 
values = np.array([1, 2, 3])
values + 10
```

Now the result is an array where 10 has been added to each element. The difference is not just syntax; it reflects the difference between Python’s built-in list type and NumPy’s array type. Understanding these distinctions helps you choose the right structure for your analysis and respond to errors with informed decisions rather than trial and error.

When errors are more complex, IPython’s interactive debugger can help you inspect state. You can pause execution, check variable values, and step through code. This is particularly useful in notebook workflows where you might be experimenting with data transformations that have many intermediate steps. Debugging is a skill, and the interactive environment gives you the tools to develop it.

## Timing, Profiling, and Performance Awareness

Data analysis often involves large datasets, and performance can become important. IPython provides easy tools for timing and profiling, which help you understand where your code spends time. This is not about premature optimization; it is about making informed choices when performance matters.

For example, you can compare a loop-based computation to a vectorized computation:


```
import numpy as np 
data = np.random.randn(100000) 

def loop_sum(values):
    total = 0.0
    for v in values:
        total += v
    return total 

%time loop_sum(data)
%time data.sum()
```

The first approach sums values using a Python loop, while the second uses NumPy’s built-in method. The vectorized approach is usually faster because it uses optimized C code under the hood. Seeing the timing difference makes the performance model concrete and helps you decide when vectorization is worth it. It also helps you understand why libraries like NumPy and pandas are central to efficient data work.

Profiling tools let you dig deeper when code is slow. They show which functions are called and how much time each consumes. This kind of insight is useful in production analytics pipelines, but even in exploratory work, it can guide you toward more efficient patterns.

## Writing Clean, Durable Analysis Code

The interactive environment makes it easy to try ideas quickly, but long-term clarity still matters. Use meaningful variable names, keep related operations close together, and avoid hidden state when possible. If a sequence of operations is important, consider wrapping it in a function or documenting it clearly in a notebook cell. This makes your analysis easier to read and easier to trust.

Here is a small example that emphasizes clarity:


```
import pandas as pd 
sales = pd.Series([120, 150, 130, 170], index=["Q1", "Q2", "Q3", "Q4"])
growth = sales.pct_change()
growth
```

The code creates a series indexed by quarter, computes the percentage change, and returns the result. The names sales and growth describe the data clearly, and the method pct_change() expresses the intent. This is the kind of readability that supports collaboration and long-term maintenance, which matters when analyses become part of decision-making processes.
