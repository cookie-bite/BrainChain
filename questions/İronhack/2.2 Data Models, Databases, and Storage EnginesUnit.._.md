# Data Models, Databases, and Storage Engines

## Introduction

In the previous lesson, you learned where data comes from and how it is encoded in formats like CSV, JSON, and Parquet. But storing raw bytes is only half the story. Before you can retrieve data efficiently, you need to decide how that data is organized: what relationships exist between items, how you express queries, and what guarantees the system provides when multiple processes read and write at the same time. These decisions belong to the world of data models and storage engines.

A **data model** describes how data is represented and related. A **storage engine** implements how that data is physically stored on machines and how it is retrieved. Together, they determine the kinds of questions you can ask easily, the performance you can expect, and the trade-offs you live with every day. In this lesson, we will explore three major data models — relational, document, and graph — and then examine how databases implement these models with different optimization goals.

By the end, you will be able to look at a data problem and reason about which model fits it best, understand the difference between transactional and analytical workloads, and appreciate why modern systems are blurring the lines between these categories.

## The Relational Model

The relational model is one of the most enduring ideas in computer science. Proposed by Edgar F. Codd in 1970, it is still the dominant model for structured data more than fifty years later. The core idea is elegant: data is organized into relations, where each relation is a set of tuples. In everyday terms, a relation is a table, and each row in that table is a tuple.

### Tables, Rows, and the Power of Simplicity

A table in the relational model has a fixed set of columns, and every row follows the same schema. The order of rows does not matter, and the order of columns does not matter. You can shuffle both without changing the relation. This mathematical foundation gives relational databases their rigor and predictability.

Let's build a concrete example. Suppose you are modeling an online bookstore:


```
import pandas as pd

books = pd.DataFrame({
    "book_id": [1, 2, 3, 4, 5],
    "title": ["Harry Potter", "Harry Potter", "Sherlock Holmes", "The Hobbit", "Sherlock Holmes"],
    "author": ["J.K. Rowling", "J.K. Rowling", "Conan Doyle", "J.R.R. Tolkien", "Conan Doyle"],
    "format": ["Paperback", "E-book", "Paperback", "Paperback", "E-book"],
    "publisher": ["Banana Press", "Banana Press", "Guava Press", "Banana Press", "Guava Press"],
    "country": ["UK", "UK", "US", "UK", "US"],
    "price": [20, 10, 30, 30, 15],
})

print(books.to_string(index=False))
```

This table works, but look at the redundancy. `"Banana Press"` and `"UK"` appear three times. `"Guava Press"` and `"US"` appear twice. If the publisher changes its name or moves to a different country, you have to update multiple rows and hope you do not miss any. This is where normalization enters the picture.

### Normalization: Reducing Redundancy

Normalization is the process of restructuring a relation to eliminate redundancy. The idea is to separate data into multiple tables so that each fact is stored in exactly one place. For our bookstore, we split publisher information into its own table:


```
books_normalized = pd.DataFrame({
    "book_id": [1, 2, 3, 4, 5],
    "title": ["Harry Potter", "Harry Potter", "Sherlock Holmes", "The Hobbit", "Sherlock Holmes"],
    "author": ["J.K. Rowling", "J.K. Rowling", "Conan Doyle", "J.R.R. Tolkien", "Conan Doyle"],
    "format": ["Paperback", "E-book", "Paperback", "Paperback", "E-book"],
    "publisher_id": [1, 1, 2, 1, 2],
    "price": [20, 10, 30, 30, 15],
})

publishers = pd.DataFrame({
    "publisher_id": [1, 2],
    "name": ["Banana Press", "Guava Press"],
    "country": ["UK", "US"],
})

print("Books:")
print(books_normalized.to_string(index=False))
print("\nPublishers:")
print(publishers.to_string(index=False))
```

Now `"Banana Press"` appears exactly once in the publishers table. If the name changes, you update a single row. The connection between a book and its publisher is maintained through the `publisher_id` foreign key. To reconstruct the full picture, you join the tables:


```
full = books_normalized.merge(publishers, on="publisher_id")
print(full.to_string(index=False))
```

The join brings the data back together. This is the fundamental trade-off of normalization: you reduce redundancy and improve consistency, but you pay the cost of joining tables when you need the complete picture. For small tables, joins are fast. For tables with millions or billions of rows, joins can become a significant bottleneck.

### SQL: A Declarative Query Language

The standard language for querying relational databases is SQL (Structured Query Language). SQL is a **declarative** language, which means you specify *what* data you want, not *how* to get it. This is fundamentally different from Python, which is **imperative**: you write step-by-step instructions for the computer to follow.

Consider the difference. In Python, to find all books under $25, you might write:


```
cheap_books = []
for _, row in books.iterrows():
    if row["price"] < 25:
        cheap_books.append(row["title"])

print(cheap_books)
```

The equivalent in SQL would be:

```sql
SELECT title FROM books WHERE price < 25;

```

The SQL version says nothing about loops, iterators, or list construction. It declares the pattern of data you want, and the database figures out the most efficient way to retrieve it. This separation between "what" and "how" is powerful because it allows the database to optimize execution behind the scenes.

The component that performs this optimization is called a **query optimizer**. A query optimizer examines all possible ways to execute a query — which indexes to use, what order to join tables, whether to scan sequentially or use a lookup — and picks the fastest approach. Developing a good query optimizer is one of the hardest problems in database engineering, but the benefit is enormous: once you have one, every application connected to the database gets the optimization for free.

This idea has inspired a parallel movement in ML. Declarative ML frameworks like Ludwig and H2O AutoML let users specify what they want (features, task, target) without writing the training code. The system experiments with architectures and hyperparameters automatically:


```
# Conceptual example of declarative ML with H2O AutoML
# x = train.columns; y = "response"
# aml = H2OAutoML(max_models=20, seed=1)
# aml.train(x=x, y=y, training_frame=train)
# aml.leader  # best-performing model
```

While declarative ML can be useful, the biggest challenges in production ML — feature engineering, data quality, drift detection, continual learning — lie outside what these frameworks automate today.

## The Document Model

The relational model works beautifully for structured, interconnected data. But it demands that your data follows a strict, predefined schema. When requirements change frequently or when data comes from sources with varying structures, this rigidity becomes a burden. In a 2014 survey, frustration with schema management was the number one reason developers adopted non-relational databases.

The document model takes a different approach. Instead of organizing data into rows within a fixed table schema, it stores each entity as a self-contained document, typically encoded as JSON, XML, or a binary variant like BSON.

### Documents as Self-Contained Units

Let's represent our bookstore data as documents:


```
import json

book_documents = [
    {
        "title": "Harry Potter",
        "author": "J.K. Rowling",
        "publisher": {"name": "Banana Press", "country": "UK"},
        "editions": [
            {"format": "Paperback", "price": 20},
            {"format": "E-book", "price": 10}
        ]
    },
    {
        "title": "Sherlock Holmes",
        "author": "Conan Doyle",
        "publisher": {"name": "Guava Press", "country": "US"},
        "editions": [
            {"format": "Paperback", "price": 30},
            {"format": "E-book", "price": 15}
        ]
    },
    {
        "title": "The Hobbit",
        "author": "J.R.R. Tolkien",
        "publisher": {"name": "Banana Press", "country": "UK"},
        "editions": [
            {"format": "Paperback", "price": 30}
        ]
    }
]

print(json.dumps(book_documents[0], indent=2))
```

Notice the difference from the relational approach. All information about a book — including its publisher details and all editions — lives in a single document. There is no need to join separate tables to reconstruct the full picture. This property is called **locality**: related data is stored together, so retrieving a complete entity is fast.

### Schema Flexibility

Documents in the same collection do not need to follow the same schema. One document can have fields that another lacks entirely:


```
# These documents coexist in the same collection
doc_a = {"title": "Book A", "author": "Author A", "publisher": {"name": "Press A"}}
doc_b = {"title": "Book B", "isbn": "978-3-16-148410-0", "languages": ["en", "de", "fr"]}

print(f"doc_a keys: {list(doc_a.keys())}")
print(f"doc_b keys: {list(doc_b.keys())}")
```

This flexibility is often described as "schemaless," but that term is misleading. The application that reads the documents still assumes some structure. The difference is where the responsibility for structure lies:

* In the relational model, the database enforces the schema when data is **written**.
* In the document model, the application enforces the schema when data is **read**.

The work does not disappear; it moves.

### The Trade-Off: Locality vs. Cross-Document Queries

The document model excels when you access entities as complete units. Looking up a single book with all its details is a single document read — no joins required. But queries that cut across documents are harder. Finding all books with prices below $25 requires scanning every document, navigating into the nested editions array, and extracting prices:


```
cheap_editions = []
for doc in book_documents:
    for edition in doc["editions"]:
        if edition["price"] < 25:
            cheap_editions.append({
                "title": doc["title"],
                "format": edition["format"],
                "price": edition["price"]
            })

for item in cheap_editions:
    print(item)
```

This works, but it is less efficient than a relational query on a flat price column. And if you want to update a publisher's information, you need to find and update every document that references that publisher — the same redundancy problem that normalization solves in the relational model.

In practice, the relational and document models are converging. PostgreSQL supports JSON columns and document-style queries. MongoDB (a document database) supports joins and aggregation pipelines that resemble relational operations. Most modern database systems let you mix both models within the same system.

## The Graph Model

While the document model prioritizes self-contained entities, the graph model prioritizes the relationships between entities. A graph consists of **nodes** (entities) and **edges** (relationships between them). When the connections between data items are as important as the items themselves, the graph model shines.

### Nodes, Edges, and Traversal

Consider a social network where you want to model people, the cities they were born in, and the countries those cities belong to:


```
# Representing a simple graph as adjacency data
nodes = {
    "alice": {"type": "person", "name": "Alice Chen"},
    "bob": {"type": "person", "name": "Bob Müller"},
    "chloe": {"type": "person", "name": "Chloe He"},
    "berlin": {"type": "city", "name": "Berlin"},
    "shanghai": {"type": "city", "name": "Shanghai"},
    "new_york": {"type": "city", "name": "New York"},
    "germany": {"type": "country", "name": "Germany"},
    "china": {"type": "country", "name": "China"},
    "usa": {"type": "country", "name": "USA"},
}

edges = [
    ("alice", "born_in", "shanghai"),
    ("bob", "born_in", "berlin"),
    ("chloe", "born_in", "new_york"),
    ("shanghai", "within", "china"),
    ("berlin", "within", "germany"),
    ("new_york", "within", "usa"),
    ("alice", "lives_in", "berlin"),
    ("bob", "lives_in", "new_york"),
]

# Find everyone born in a specific country
def find_born_in_country(country_id):
    # First, find all cities in the country
    cities = [src for src, rel, tgt in edges if tgt == country_id and rel == "within"]
    # Then, find all people born in those cities
    people = [src for src, rel, tgt in edges if tgt in cities and rel == "born_in"]
    return [nodes[p]["name"] for p in people]

print("Born in China:", find_born_in_country("china"))
print("Born in USA:", find_born_in_country("usa"))
print("Born in Germany:", find_born_in_country("germany"))
```

The power of the graph model is visible in this traversal. To find everyone born in a country, you start at the country node, follow "within" edges to find cities, then follow "born_in" edges backward to find people. The number of hops between a person and a country can vary, and the graph model handles this naturally.

Try writing the equivalent query in SQL. You would need to know in advance how many hops exist between person and country, and you would need a different query for each path length. In a relational database, this kind of variable-depth traversal is either impossible or extremely awkward. In a graph database, it is the fundamental operation.

### When Graphs Fit

Graph models are the right choice when relationships are the primary subject of your queries. Common use cases include:

* **Social networks:** tracking who knows whom or follows whom.
* **Fraud detection:** tracing chains of suspicious, interconnected transactions.
* **Knowledge graphs:** connecting abstract concepts, fields, and physical entities.
* **Recommendation engines:** analyzing how similar users interacted with similar item sets.
* **Network infrastructure:** mapping physical and logical connections between devices.

The key insight across all three data models is this: many queries that are easy in one model are difficult in another. The right model depends on what questions you need to ask. If your queries are mostly about structured records and aggregations, the relational model is usually best. If your entities are self-contained and access is entity-at-a-time, the document model fits well. If relationships and traversals dominate, the graph model is your tool.

## Data Storage Engines and Processing

Data models describe the logical structure of your data. Storage engines implement the physical reality: how bytes are arranged on disk, how indexes speed up lookups, and how the system handles multiple simultaneous reads and writes. Understanding storage engines helps you choose the right database for your workload.

### Transactional Processing (OLTP)

In the digital world, a transaction is any discrete action: placing an order, posting a comment, uploading a file, requesting a ride. Even though these actions involve different types of data, they share a processing pattern: each transaction is inserted as it happens, occasionally updated, and sometimes deleted. This is online transaction processing (**OLTP**).

Transactional workloads have demanding requirements. Because transactions often involve users who are waiting for a response, they need low latency — each operation must complete in milliseconds. And because users expect the system to work at all times, the system needs high availability.

Transactional databases provide guarantees collectively known as **ACID**:

* **Atomicity:** ensures that all steps in a transaction succeed or fail as a group. If a payment fails in a ride-sharing app, you do not want a driver to be assigned anyway. Either the entire transaction completes, or none of it does.
* **Consistency:** ensures that every transaction follows predefined structural rules. A transaction must be made by a valid user, an order must reference an existing product, and account balances must never go negative.
* **Isolation:** ensures that concurrent transactions do not interfere with each other. If two users try to book the last available seat on a flight at the same time, isolation guarantees that only one succeeds.
* **Durability:** ensures that once a transaction is committed, it survives system failures. After your order completes and your phone dies, the order records must remain secure.

Let's see what transactional operations look like in code:


```
# Simulating transactional operations on an inventory
inventory = {
    "SKU-001": {"name": "Wireless Mouse", "quantity": 50, "price": 29.99},
    "SKU-002": {"name": "USB-C Cable", "quantity": 200, "price": 9.99},
    "SKU-003": {"name": "Mechanical Keyboard", "quantity": 30, "price": 89.99},
}

def process_order(sku, order_quantity):
    """Atomic transaction: reduce inventory only if sufficient stock exists."""
    if sku not in inventory:
        return {"status": "error", "message": f"Product {sku} not found"}

    product = inventory[sku]
    if product["quantity"] < order_quantity:
        return {"status": "error", "message": "Insufficient stock"}

    # Atomic update: deduct quantity
    product["quantity"] -= order_quantity
    total = product["price"] * order_quantity
    return {"status": "success", "product": product["name"], "total": total,
            "remaining": product["quantity"]}

print(process_order("SKU-001", 3))
print(process_order("SKU-001", 100))  # Should fail: not enough stock
print(process_order("SKU-999", 1))    # Should fail: product not found
```

Each call to `process_order` is atomic: it either completes the full operation (check stock, deduct quantity, compute total) or fails without making any changes. This is the essence of transactional processing.

Not all transactional databases enforce full ACID guarantees. Some developers find ACID too restrictive for their use cases. An alternative model called **BASE** (Basically Available, Soft state, Eventual consistency) relaxes these guarantees in exchange for higher availability and performance in distributed systems. The trade-off between ACID and BASE is a classic tension in database design.

### Analytical Processing (OLAP)

While transactional databases handle individual operations efficiently, a different kind of question requires a different approach. "What was the average ride fare in Berlin last month?" is not about a single transaction; it is about aggregating data across thousands or millions of records. This is online analytical processing (**OLAP**).

Analytical queries differ from transactional queries in almost every dimension:

| Property | Transactional (OLTP) | Analytical (OLAP) |
| --- | --- | --- |
| **Operations** | Insert, update, delete | Read, aggregate, scan |
| **Query scope** | One or few records | Thousands to millions |
| **Latency requirement** | Milliseconds | Seconds to minutes acceptable |
| **Access pattern** | Row-level (full records) | Column-level (specific fields) |
| **Optimization** | Write speed, consistency | Read speed, compression |

Because transactional workloads operate on individual records, transactional databases are typically row-major: all fields of a record are stored together so that inserting or reading a complete record is fast. But this layout is inefficient for analytical queries that need to scan a single column across many records.

Analytical databases use column-major storage to make these aggregation queries efficient. When all values of a column are stored contiguously, computing an average or filtering by a threshold becomes a fast sequential scan.

### The Convergence of OLTP and OLAP

Historically, organizations maintained separate databases for transactional and analytical workloads. Transactional data would be extracted periodically and loaded into an analytical data warehouse. This separation existed because of technological limitations: it was hard to build a single database that handled both workloads efficiently.

That separation is narrowing. Modern databases increasingly support both patterns. CockroachDB is a transactional database that can handle analytical queries. DuckDB is an analytical database designed for fast reads that also supports transactional guarantees. Apache Iceberg provides a table format that sits on top of existing storage and supports both workload types.

### Decoupling Storage and Compute

One of the most significant architectural shifts is the separation of storage from compute (processing). Traditionally, how data was stored determined how it was processed. Transactional databases stored data in row-major format and processed it transactionally. Analytical databases stored data in column-major format and processed it analytically.

In the decoupled paradigm, data is stored once (often in a cloud object store like Amazon S3 or Google Cloud Storage), and different processing engines can be layered on top for different query patterns. This is the approach taken by platforms like Google BigQuery, Snowflake, and Databricks.

```
Traditional (coupled):
    Transaction DB (row-major) ──→ Transactional queries
    Analytical DB (col-major)  ──→ Analytical queries
    (Same data stored twice)

Modern (decoupled):
    Shared Storage (S3, GCS)
        ├── Transactional engine ──→ Transactional queries
        └── Analytical engine    ──→ Analytical queries
    (Data stored once)

```

This decoupling reduces data duplication, simplifies architecture, and lets each processing layer evolve independently. It is directly relevant to building ML systems, where you often need both real-time feature serving (transactional) and batch training data preparation (analytical) from the same underlying data asset.

## Choosing the Right Model and Engine

With three data models and two major processing paradigms, how do you make the right choice? Here are practical guidelines:

* **Choose the relational model** when your data has clear, stable relationships and your queries involve filtering, joining, and aggregating across multiple tables. This is the default for most business applications: e-commerce, finance, user management, and inventory.
* **Choose the document model** when your entities are self-contained and rarely need cross-entity queries. Content management systems, product catalogs with varying attributes, and configuration stores are natural fits. The flexibility of schema-on-read is valuable when different records have different structures.
* **Choose the graph model** when relationships are the primary subject of your queries: social networks, fraud detection, recommendation engines, and knowledge graphs. If you find yourself writing increasingly complex joins in SQL to traverse relationships, a graph model may simplify your life.
* **Choose a transactional engine** when your workload is dominated by individual record operations that require consistency guarantees: user-facing applications, payment systems, and real-time backend services.
* **Choose an analytical engine** when your workload is dominated by aggregation, scanning, and batch computation: reporting dashboards, ML feature engineering, and business intelligence pipelines.

In practice, most production systems use multiple databases for different purposes. A ride-sharing platform might use PostgreSQL for user accounts (relational, transactional), MongoDB for driver profiles with flexible schemas (document), a graph database for matching riders with nearby drivers (graph), and an analytical data warehouse for computing high-level business metrics (analytical). The skill is not choosing one model for everything; it is knowing which model fits each part of your system.

## Summary

In this lesson, you explored the three major data models that shape how information is organized and queried, and the storage engines that implement them.

* **The relational model** organizes data into tables with fixed schemas, supports normalization to eliminate redundancy, and uses SQL as a powerful declarative query language. Its strength is structured, interconnected data with complex query requirements.
* **The document model** stores self-contained entities that can have flexible, varying schemas. It provides excellent locality for entity-level access but makes cross-document queries more expensive. It is converging with the relational model in modern database systems.
* **The graph model** makes relationships first-class citizens, enabling efficient traversal queries that would be difficult or impossible in relational systems. It excels when connections between data points are as important as the data points themselves.
* **On the storage engine side**, transactional databases optimize for individual record operations with low latency and ACID guarantees, while analytical databases optimize for large-scale aggregation and scanning with column-major storage. The traditional separation between these two paradigms is narrowing as modern systems decouple storage from compute, allowing different processing engines to share the same underlying data.
