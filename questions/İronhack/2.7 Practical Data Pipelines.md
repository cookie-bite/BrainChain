# Practical Data Pipelines

## Introduction

Over the last several lessons, you have learned how to source data, choose formats, model storage, build ETL workflows, create labeled datasets, and clean messy real-world data. Each of these skills addresses one piece of the puzzle. In production, they all have to work together — continuously, reliably, and at scale. That is what a data pipeline does.

A data pipeline is the end-to-end system that moves data from where it originates to where it is consumed: by analysts, dashboards, ML models, or other systems. Building a pipeline that works once is straightforward. Building one that works every day, handles failures gracefully, and produces data you can trust is an engineering challenge. This lesson is about that challenge.

We will examine the anatomy of production data pipelines, the distinction between offline and online data paths, how to separate storage from compute, how to manage dataset refresh cycles, and how to trace data and label origins across the entire system. The goal is for you to look at a pipeline architecture diagram and understand not just what each component does, but why it is there and what breaks if you remove it.

## Anatomy of an End-to-End Data Pipeline

A production data pipeline typically has five stages, each with distinct responsibilities. Understanding these stages helps you reason about where problems occur and where to add safeguards.

### Stage 1: Ingestion

Ingestion is how data enters the pipeline. Sources vary widely: user interactions from an application, logs from servers, API responses from third-party services, files uploaded by partners, or rows arriving from a streaming platform. The ingestion layer must handle:

* Multiple formats — JSON from APIs, CSV from uploads, Protobuf from internal services
* Variable throughput — Black Friday traffic is nothing like a Tuesday at 3 AM
* Partial failures — one data source goes down while others continue

A well-designed ingestion layer decouples the source from the rest of the pipeline. It writes raw data into a staging area (a landing zone) without transforming it. This preserves the original data so you can reprocess it if downstream logic changes.


```
# Conceptual ingestion: write raw records to a staging area
import json
from pathlib import Path
from datetime import datetime

def ingest_record(record, landing_zone="data/raw"):
    """Write a single raw record to the landing zone with a timestamp."""
    Path(landing_zone).mkdir(parents=True, exist_ok=True)
    timestamp = datetime.utcnow().strftime("%Y%m%d_%H%M%S_%f")
    path = Path(landing_zone) / f"record_{timestamp}.json"
    path.write_text(json.dumps(record), encoding="utf-8")
    return path

# Example: ingesting one transaction
record = {
    "InvoiceNo": "536365",
    "StockCode": "85123A",
    "Description": "WHITE HANGING HEART T-LIGHT HOLDER",
    "Quantity": 6,
    "InvoiceDate": "2010-12-01 08:26:00",
    "UnitPrice": 2.55,
    "CustomerID": 17850.0,
    "Country": "United Kingdom",
}
path = ingest_record(record)
print(f"Ingested to: {path}")
```

### Stage 2: Validation

Raw data cannot be trusted. Validation checks whether incoming data meets the expected schema, value ranges, and business rules. Failed validation should quarantine bad records rather than silently dropping them — you want to know what failed and why.


```
def validate_transaction(record):
    """Validate a single transaction record. Returns (is_valid, errors)."""
    errors = []

    # Schema checks
    required_fields = ["InvoiceNo", "StockCode", "Quantity", "UnitPrice"]
    for field in required_fields:
        if field not in record or record[field] is None:
            errors.append(f"missing_field:{field}")

    # Value range checks
    if "Quantity" in record and record["Quantity"] is not None:
        if not isinstance(record["Quantity"], (int, float)):
            errors.append("invalid_type:Quantity")
        elif record["Quantity"] == 0:
            errors.append("zero_quantity")

    if "UnitPrice" in record and record["UnitPrice"] is not None:
        if record["UnitPrice"] < 0:
            errors.append("negative_price")

    # Business rule: cancellations have "C" prefix and negative quantity
    invoice = record.get("InvoiceNo", "")
    qty = record.get("Quantity", 0)
    if str(invoice).startswith("C") and qty > 0:
        errors.append("cancellation_with_positive_quantity")

    return len(errors) == 0, errors
```

### Stage 3: Transformation

Transformation converts validated raw data into the format required by downstream consumers. This is the "T" in ETL. Common transformations include:

* Cleaning — handling missing values, removing duplicates, fixing inconsistent formats
* Enrichment — joining with reference data (product catalogs, customer profiles)
* Aggregation — computing daily totals, rolling averages, customer-level summaries
* Feature engineering — creating derived columns for ML models

The key principle is idempotency: running the same transformation twice on the same input should produce the same output. This means you can safely re-run transformations after fixing a bug without worrying about double-counting.


```
import pandas as pd

def transform_transactions(df):
    """Transform raw transactions into analysis-ready format."""
    df = df.copy()

    # Clean: remove rows with missing CustomerID
    df = df.dropna(subset=["CustomerID"])

    # Derive: total line amount
    df["line_total"] = df["Quantity"] * df["UnitPrice"]

    # Derive: flag cancellations
    df["is_cancellation"] = df["InvoiceNo"].astype(str).str.startswith("C")

    # Derive: extract date components
    df["InvoiceDate"] = pd.to_datetime(df["InvoiceDate"])
    df["date"] = df["InvoiceDate"].dt.date
    df["hour"] = df["InvoiceDate"].dt.hour

    return df
```

### Stage 4: Storage

Transformed data needs to be stored where consumers can access it efficiently. The storage choice depends on the access pattern:

* Analytical queries (BI dashboards, ad-hoc analysis) $\rightarrow$ columnar formats like Parquet, or an analytical database like DuckDB
* ML training $\rightarrow$ versioned datasets in Parquet or a feature store
* Real-time serving $\rightarrow$ a key-value store or an online feature store
* Archival $\rightarrow$ compressed files in object storage (S3, GCS)

A common pattern is to maintain multiple storage layers: a raw layer (original data, never modified), a clean layer (validated and transformed), and a feature layer (aggregated and ready for ML). This layered approach lets you reprocess from any point if something goes wrong.

### Stage 5: Monitoring and Quality

A pipeline that runs without monitoring is a pipeline that fails silently. Quality monitoring should check:

* Freshness — is data arriving on schedule? A missing batch at 2 AM might mean the source system is down.
* Volume — did today's batch have roughly the expected number of records? A sudden 90% drop signals a problem.
* Schema — did the schema change? A new column or a changed data type can break downstream consumers.
* Distribution — did the statistical properties of the data change? A sudden shift in the average transaction value might indicate a data quality issue or a real business event.


```
def check_data_quality(df, expected_min_rows=100):
    """Run basic quality checks on a transformed DataFrame."""
    checks = {}

    checks["row_count"] = len(df)
    checks["row_count_ok"] = len(df) >= expected_min_rows

    checks["null_pct"] = df.isnull().mean().to_dict()
    checks["high_null_columns"] = [
        col for col, pct in checks["null_pct"].items() if pct > 0.1
    ]

    # Distribution check: flag if mean line_total changes dramatically
    if "line_total" in df.columns:
        checks["mean_line_total"] = df["line_total"].mean()

    checks["all_ok"] = checks["row_count_ok"] and len(checks["high_null_columns"]) == 0
    return checks
```

## Offline vs. Online Data Paths

Production ML systems typically maintain two separate data paths that serve different purposes.

### The Offline Path (Batch)

The offline path processes data in large batches — hourly, daily, or weekly. This is where you train ML models, compute historical features, build dashboards, and run analytical queries. Offline processing prioritizes throughput: process as much data as possible in a reasonable time window.

A typical offline pipeline looks like:

```
Raw data ──→ Batch validation ──→ Batch transformation ──→ Analytical storage ──→ ML training

```

The entire history is available, so you can compute features that look backwards in time (e.g., "average spending over the last 90 days"). Offline features are sometimes called static features because they are precomputed and do not change until the next batch run.

### The Online Path (Real-Time)

The online path processes data as it arrives — one record at a time, with latency requirements measured in milliseconds or seconds. This is where you serve ML predictions, compute real-time features, and trigger alerts. Online processing prioritizes latency: respond as fast as possible.

A typical online pipeline looks like:

```
New event ──→ Stream validation ──→ Real-time transformation ──→ Feature store ──→ Model serving

```

Online features are sometimes called dynamic features because they update with every new event (e.g., "number of transactions in the last 5 minutes").

### Bridging the Two Paths

Most production systems need both paths. A fraud detection system, for example, uses offline features (customer's historical spending pattern) combined with online features (number of transactions in the last 10 minutes) to make a real-time decision. The challenge is keeping the two paths consistent — the features used during training (offline) must match the features used during serving (online). This mismatch is called training-serving skew and is a common source of production bugs.

## Separation of Storage and Compute

Traditional databases bundle storage and compute together: the same machine stores the data and executes queries. Modern data systems increasingly decouple them. Your data lives in cheap object storage (like Amazon S3 or Google Cloud Storage), and you spin up compute resources only when you need to process it.

This separation has several advantages:

* Cost — storage is cheap; compute is expensive. You pay for compute only when you use it.
* Scalability — you can scale storage and compute independently. Need to store 10x more data? Add storage. Need to run queries 10x faster? Add more compute workers.
* Flexibility — multiple compute engines (pandas, DuckDB, Spark) can read from the same storage layer.

In practice, this looks like:

```
Data lake (Parquet files on S3)
  ├── DuckDB (ad-hoc analytics)
  ├── Spark (large-scale batch processing)
  ├── pandas (local exploration)
  └── ML training pipeline (reads features from Parquet)

```

The trade-off is added complexity: you need to manage data access, permissions, and consistency across compute engines. But for most organizations beyond a single-machine scale, the benefits outweigh the costs.

## Dataset Refresh and Update Cycles

Production pipelines do not run once. They run on schedules: hourly, daily, weekly. The refresh cycle determines how current your data is, which directly affects model performance and business decisions.

### Full Refresh vs. Incremental Updates

A full refresh reprocesses all historical data from scratch every time the pipeline runs. This is simple and guaranteed to be consistent, but expensive for large datasets. It works well when data is small enough to reprocess quickly or when you need to backfill after a logic change.

An incremental update processes only the new data that arrived since the last run. This is efficient but more complex: you need to track what has already been processed, handle late-arriving data, and merge new results with existing ones.


```
# Incremental update pattern: track the high-water mark
import json
from datetime import datetime

def get_high_water_mark(state_file="pipeline_state.json"):
    """Get the timestamp of the last successfully processed record."""
    try:
        with open(state_file) as f:
            state = json.load(f)
        return datetime.fromisoformat(state["last_processed"])
    except (FileNotFoundError, KeyError):
        return datetime.min

def update_high_water_mark(timestamp, state_file="pipeline_state.json"):
    """Update the high-water mark after successful processing."""
    with open(state_file, "w") as f:
        json.dump({"last_processed": timestamp.isoformat()}, f)

# Usage
hwm = get_high_water_mark()
new_data = [r for r in all_records if r["timestamp"] > hwm]
if new_data:
    process(new_data)
    update_high_water_mark(max(r["timestamp"] for r in new_data))
```

### Late-Arriving Data

In production, data does not always arrive in order. A transaction from Monday might show up in Wednesday's batch because of a network delay or a partner system's processing lag. Your pipeline needs a strategy for late arrivals:

* Ignore them — simplest but loses data
* Reprocess the affected window — correct but expensive
* Append and reconcile — add the late data and adjust aggregates

The right strategy depends on your tolerance for stale data and the cost of reprocessing.

## Tracing Data and Label Origins

When a model makes a wrong prediction, you need to trace back: what training data did it learn from? Where did that data come from? Who labeled it? What transformations were applied? This is data lineage, and it is essential for debugging, compliance, and trust.

### What to Track

At minimum, track these for every dataset used in training or serving:

* Source — where did each record originate? (which system, which API, which file)
* Ingestion timestamp — when did it enter the pipeline?
* Transformations applied — which cleaning rules, enrichment joins, and aggregations were applied, and in what order?
* Labels — who or what assigned the label? (human annotator, labeling function, natural label from user behavior)
* Versioning — which version of the pipeline code produced this output?

### Practical Lineage Tracking

You do not need a complex lineage system to start. A simple metadata file alongside each output dataset goes a long way:


```
import json
from datetime import datetime

def write_lineage(output_path, source_files, transform_version, row_count):
    """Write a lineage metadata file alongside the output dataset."""
    lineage = {
        "output": str(output_path),
        "created_at": datetime.utcnow().isoformat(),
        "sources": source_files,
        "transform_version": transform_version,
        "row_count": row_count,
        "pipeline_run_id": datetime.utcnow().strftime("%Y%m%d_%H%M%S"),
    }
    lineage_path = str(output_path) + ".lineage.json"
    with open(lineage_path, "w") as f:
        json.dump(lineage, f, indent=2)
    return lineage_path

# Example
write_lineage(
    output_path="data/clean/transactions_2024_01.parquet",
    source_files=["data/raw/batch_2024_01_01.json", "data/raw/batch_2024_01_02.json"],
    transform_version="v2.3.1",
    row_count=54321,
)
```

### Why Lineage Matters

Without lineage, debugging is guesswork. Consider these scenarios:

* Your model's performance drops after a pipeline update. Was it the new cleaning logic? A change in the source data? A labeling issue? Without lineage, you cannot tell.
* A regulatory audit asks which customer records were used to train a model. Without lineage, you cannot answer.
* You discover that a labeling function was buggy for two weeks. Which models were trained on the affected data? Without lineage, you have to retrain everything "just in case."

Lineage converts these nightmares into straightforward investigations: trace from the model back to its training data, from the training data back to its sources and labels, and identify exactly what was affected.

## Failure Modes and Resilience

Production pipelines fail. The question is not if but how. Good pipeline design anticipates failure and limits its blast radius.

### Common Failure Points

* Source unavailability — an API is down, a file is not uploaded, a database is under maintenance
* Schema changes — a source system adds or removes a column without warning
* Data quality degradation — valid records but with shifted distributions, increased nulls, or corrupted values
* Compute failures — out of memory, timeout, network partition
* Downstream dependency breaks — a consumer expects a specific format that your latest change altered

### Resilience Patterns

* **Retry with backoff:** Transient failures (network blips, temporary API errors) often resolve themselves. Retry failed operations with exponential backoff before giving up.
* **Dead letter queues:** Records that fail validation or transformation go to a quarantine area instead of being silently dropped. You can inspect and reprocess them later.
* **Checkpointing:** For long-running transformations, save progress at intervals so you can resume from the last checkpoint instead of starting over.
* **Idempotent operations:** Design every stage so that running it twice produces the same result. This means you can safely retry any stage without fear of duplicate data.
* **Alerting:** Set up alerts for missing data, unexpected volumes, schema changes, and quality metric violations. The alert should tell you what went wrong and where, not just that "something failed."

## Summary

* A production data pipeline is a system of five stages — ingestion, validation, transformation, storage, and monitoring — each with distinct responsibilities and failure modes.
* Offline and online paths serve different needs. Offline pipelines process data in batches for training and analytics (throughput-oriented). Online pipelines process data in real time for serving and alerting (latency-oriented). Bridging them consistently is one of the hardest problems in production ML.
* Separation of storage and compute lets you scale and cost-optimize independently. Data lives in cheap storage; compute spins up on demand.
* Refresh cycles determine data freshness. Full refreshes are simple but expensive; incremental updates are efficient but complex. Late-arriving data requires explicit handling strategies.
* Data lineage traces every record from origin through transformation to consumption. It is essential for debugging, compliance, and trust. Start simple with metadata files; grow into a formal lineage system as your pipelines mature.
* Resilience comes from anticipating failure: retries, dead letter queues, checkpoints, idempotency, and alerting. A pipeline that cannot fail gracefully is not production-ready.
