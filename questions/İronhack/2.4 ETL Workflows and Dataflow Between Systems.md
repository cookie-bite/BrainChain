# ETL Workflows and Dataflow Between Systems

## Introduction

In the previous lessons, you learned how data is represented in different formats, how data models organize information, and how modern analytical engines process queries efficiently. All of those lessons assumed that data exists within a single process or a single file. In reality, production systems rarely work this way. Data is generated in one place, processed in another, and consumed in a third. A feature engineering service computes features from raw data, a prediction service generates predictions based on those features, and a monitoring service tracks how well those predictions perform. Each of these is a separate process, and data must flow between them.

This lesson examines how data moves through real systems. We will cover the ETL process — the foundational workflow for getting data from sources to analytical destinations — and then explore three modes of dataflow between processes: through databases, through services, and through real-time transports. We will finish with the distinction between batch and stream processing, which determines how quickly your system reacts to new data.

These concepts are essential for anyone building ML systems in production, where the pipeline that delivers data to your model is often more complex and more fragile than the model itself.

## ETL: Extract, Transform, Load

The most fundamental pattern for moving data from its source to an analytical destination is ETL: Extract, Transform, Load. Despite being decades old, ETL remains the backbone of data processing at most organizations. Understanding it clearly gives you a framework for thinking about any data pipeline.

### Extract: Getting Data from Sources

The first step is extracting data from wherever it lives. This might mean reading files from a storage bucket, querying a database, hitting an API, or consuming a stream. Each source has its own quirks: APIs have rate limits, databases have schema changes, files might be malformatted, and streams can arrive out of order.

The extraction phase should include validation. Catching problems early — corrupted files, unexpected schemas, missing fields — saves enormous effort downstream. If you reject bad data at the extraction point and notify the source, you avoid the situation where a data quality problem silently propagates through your entire pipeline and surfaces as a mysterious model accuracy drop days later.


```
import json

# Simulating extraction from a raw data source
raw_records = [
    '{"user_id": "u001", "event": "purchase", "amount": 29.99, "ts": "2025-03-15T10:23:00"}',
    '{"user_id": "u002", "event": "purchase", "amount": -5.00, "ts": "2025-03-15T10:24:00"}',
    '{"user_id": "u003", "event": "purchase", "ts": "2025-03-15T10:25:00"}',  # missing amount
    'this is not json at all',
    '{"user_id": "u004", "event": "purchase", "amount": 149.50, "ts": "2025-03-15T10:26:00"}',
]

valid_records = []
rejected_records = []

for i, raw in enumerate(raw_records):
    try:
        record = json.loads(raw)
        # Validate required fields
        if "amount" not in record:
            rejected_records.append((i, "missing_field", raw))
        elif record["amount"] < 0:
            rejected_records.append((i, "invalid_value", raw))
        else:
            valid_records.append(record)
    except json.JSONDecodeError:
        rejected_records.append((i, "parse_error", raw))

print(f"Extracted: {len(valid_records)} valid, {len(rejected_records)} rejected")
for idx, reason, data in rejected_records:
    print(f"  Rejected record {idx}: {reason}")
```

This validation logic catches three common problems: invalid JSON, missing required fields, and values that fail business rules (negative purchase amounts). In production, you would log the rejected records for investigation and potentially alert the upstream team.

### Transform: Shaping Data for Its Destination

The transform step is where most of the work happens. This is where you clean data, standardize formats, join data from multiple sources, compute derived features, deduplicate records, and apply any business logic needed to make the data ready for analysis.


```
import pandas as pd
from datetime import datetime

# Transform the extracted records
df = pd.DataFrame(valid_records)

# Parse timestamps
df["ts"] = pd.to_datetime(df["ts"])

# Standardize event names
df["event"] = df["event"].str.lower().str.strip()

# Derive new features
df["date"] = df["ts"].dt.date
df["hour"] = df["ts"].dt.hour

# Categorize amounts
df["amount_tier"] = pd.cut(
    df["amount"],
    bins=[0, 25, 100, float("inf")],
    labels=["small", "medium", "large"])

print(df.to_string(index=False))
```

The transformation step often needs to combine data from multiple sources. For example, you might join purchase events with user profile data to add demographic features, or with product catalog data to add category information:


```
# Simulating a join with user profile data
user_profiles = pd.DataFrame({
    "user_id": ["u001", "u002", "u003", "u004"],
    "country": ["Germany", "Korea", "Kenya", "Canada"],
    "signup_date": pd.to_datetime(["2024-01-15", "2024-06-20", "2025-01-10", "2024-11-05"]),
})

# Enrich purchase data with user profiles
enriched = df.merge(user_profiles, on="user_id", how="left")
print(enriched[["user_id", "event", "amount", "country", "amount_tier"]].to_string(index=False))
```

Common transformation operations include deduplication (removing duplicate records that arrive from retries or multiple sources), standardization (converting codes to descriptive categories), aggregation (computing totals or averages over a period), and feature derivation.

### Load: Writing to the Destination

The final step is loading the transformed data into its target destination. This might be a data warehouse for analytical queries, a feature store for ML model serving, a database for application use, or a Parquet file for batch processing.


```
# Load to Parquet (a common analytical destination)
enriched.to_parquet("purchases_enriched.parquet", index=False)
print(f"Loaded {len(enriched)} records to purchases_enriched.parquet")

# In production, you might also load to a database:
# enriched.to_sql("purchases", connection, if_exists="append", index=False)
```

The loading step needs to handle decisions about how to integrate new data with existing data. Do you append new records to the existing table? Do you replace the entire table? Do you merge updates based on a key? These choices depend on the nature of your data and your freshness requirements.

### ETL vs ELT: When to Transform

The traditional ETL pattern transforms data before loading it, which means only clean, structured data enters the destination. This keeps the analytical store organized and queryable but requires upfront schema decisions.

An alternative pattern, ELT (Extract, Load, Transform), loads raw data into a data lake first and transforms it later. This approach gained popularity with the growth of cheap cloud storage and powerful analytical engines that can process unstructured data efficiently.

```
ETL: Source ──→ Extract ──→ Transform ──→ Load ──→ Warehouse (structured)

ELT: Source ──→ Extract ──→ Load ──→ Data Lake (raw) ──→ Transform ──→ Analytical tables

```

The trade-off is clear. ETL enforces quality and structure early, making downstream queries fast and reliable. ELT prioritizes fast ingestion and flexibility, but means you have to deal with messy raw data when you query the lake. In practice, many organizations use both: ELT for initial capture and ETL for preparing specific analytical datasets.

Modern data lakehouse platforms (Databricks, Snowflake) blur this distinction by supporting both raw data storage and structured analytical tables in the same system, letting you choose transformation timing on a case-by-case basis.

## Modes of Dataflow Between Processes

ETL describes the pattern of data processing. But how does data actually move between the processes that implement each step? In production, these steps often run as separate services on different machines. There are three primary modes of dataflow: through databases, through services, and through real-time transports.

### Data Passing Through Databases

The simplest way to move data between two processes is to have one write to a database and the other read from it. Process A computes a result, stores it in a shared database, and Process B retrieves it when needed.


```
# Conceptual example: Process A writes features to a store
feature_store = {}  # Simulating a shared database

def process_a_compute_features(user_id, purchases):
    """Feature engineering service: computes and stores features."""
    features = {
        "total_spent": sum(p["amount"] for p in purchases),
        "num_purchases": len(purchases),
        "avg_purchase": sum(p["amount"] for p in purchases) / len(purchases),
    }
    feature_store[user_id] = features
    return features

# Process A stores computed features
process_a_compute_features("u001", [{"amount": 29.99}, {"amount": 15.50}])
process_a_compute_features("u004", [{"amount": 149.50}])

# Process B reads features for prediction
def process_b_predict(user_id):
    """Prediction service: reads features and generates predictions."""
    features = feature_store.get(user_id)
    if features is None:
        return {"error": "Features not found"}
    # Simple prediction logic (placeholder)
    risk_score = features["avg_purchase"] / 100.0
    return {"user_id": user_id, "risk_score": round(risk_score, 3)}

print(process_b_predict("u001"))
print(process_b_predict("u004"))
```

This approach is simple and works well when latency requirements are moderate. But it has two limitations. First, both processes must have access to the same database, which may not be feasible across organizational boundaries. Second, database reads and writes are not instantaneous. For applications where every millisecond counts — like serving real-time predictions to users — the overhead of database access can be too high.

### Data Passing Through Services

A more direct approach is for one process to request data from another over a network. This is the foundation of the service-oriented architecture and its modern incarnation, microservices.

In a microservice architecture, each component of your application runs as an independent service that exposes an API. Services communicate by sending requests to each other, typically using REST (Representational State Transfer) or RPC (Remote Procedure Call) protocols.

Consider a ride-sharing platform with three services:


```
# Simulating a microservice architecture for ride pricing

class DriverManagementService:
    """Predicts available drivers in an area."""
    def get_available_drivers(self, area):
        # In production: ML model prediction
        simulated_drivers = {"downtown": 15, "airport": 8, "suburbs": 22}
        return simulated_drivers.get(area, 5)

class RideManagementService:
    """Predicts ride demand in an area."""
    def get_ride_demand(self, area):
        # In production: ML model prediction
        simulated_demand = {"downtown": 30, "airport": 12, "suburbs": 10}
        return simulated_demand.get(area, 8)

class PriceOptimizationService:
    """Optimizes ride price based on supply and demand."""
    def __init__(self, driver_service, ride_service):
        self.driver_service = driver_service
        self.ride_service = ride_service

    def get_optimal_price(self, area, base_price=10.0):
        # Request data from other services
        available = self.driver_service.get_available_drivers(area)
        demand = self.ride_service.get_ride_demand(area)

        # Price is based on supply/demand ratio
        if available == 0:
            return {"area": area, "price": base_price * 5, "surge": 5.0}

        ratio = demand / available
        surge = max(1.0, min(ratio, 5.0))  # Cap surge at 5x
        price = round(base_price * surge, 2)

        return {"area": area, "price": price, "surge": round(surge, 1),
                "drivers": available, "demand": demand}

# Wire up the services
driver_svc = DriverManagementService()
ride_svc = RideManagementService()
price_svc = PriceOptimizationService(driver_svc, ride_svc)

# Each price request triggers calls to the other two services
for area in ["downtown", "airport", "suburbs"]:
    result = price_svc.get_optimal_price(area)
    print(f"{area}: ${result['price']} (surge: {result['surge']}x, "
          f"drivers: {result['drivers']}, demand: {result['demand']})")
```

In this architecture, each time a user requests a ride, the price optimization service makes requests to both the driver management and ride management services. This request-driven communication is synchronous: the price service waits for responses before it can compute the price.

The synchronous nature of service-to-service communication creates a dependency chain. If the driver management service goes down, the price optimization service cannot complete its work. If one service is slow, all services that depend on it slow down.

The two most common protocols for service communication are:

* **REST (Representational State Transfer):** Designed for network communication and is the dominant style for public APIs. REST uses standard HTTP methods (GET, POST, PUT, DELETE) and is language-agnostic.
* **RPC (Remote Procedure Call):** Makes remote service calls look like local function calls. It is faster than REST for internal communication. gRPC (Google's RPC framework) uses Protocol Buffers for efficient serialization.

### Data Passing Through Real-Time Transports

The limitations of request-driven communication become apparent when many services need to share data with each other. If three services each need data from the other two, you already have six direct connections. With ten services, you have up to ninety. This complexity explodes as systems grow.

Real-time transports solve this by introducing a broker that mediates all data passing. Instead of services communicating directly, each service publishes data to the broker, and any service that needs that data subscribes to it.


```
# Simulating a publish-subscribe (pubsub) message broker

class MessageBroker:
    """Simple in-memory pubsub broker."""
    def __init__(self):
        self.topics = {}       # topic -> list of messages
        self.subscribers = {}  # topic -> list of callback functions

    def publish(self, topic, message):
        if topic not in self.topics:
            self.topics[topic] = []
        self.topics[topic].append(message)
        # Notify subscribers
        for callback in self.subscribers.get(topic, []):
            callback(message)

    def subscribe(self, topic, callback):
        if topic not in self.subscribers:
            self.subscribers[topic] = []
        self.subscribers[topic].append(callback)

    def get_latest(self, topic):
        messages = self.topics.get(topic, [])
        return messages[-1] if messages else None

# Create broker
broker = MessageBroker()

# Driver service publishes predictions
def driver_update(area, count):
    broker.publish("driver_availability", {"area": area, "available": count})

# Ride service publishes demand predictions
def ride_update(area, demand):
    broker.publish("ride_demand", {"area": area, "demand": demand})

# Price service subscribes to both topics
price_logs = []
def on_driver_update(msg):
    price_logs.append(f"  [Price Service] Received driver update: {msg}")

def on_ride_update(msg):
    price_logs.append(f"  [Price Service] Received ride update: {msg}")

broker.subscribe("driver_availability", on_driver_update)
broker.subscribe("ride_demand", on_ride_update)

# Simulate activity
driver_update("downtown", 15)
ride_update("downtown", 30)
driver_update("airport", 8)
ride_update("airport", 12)

for log in price_logs:
    print(log)
```

In this event-driven architecture, each data update is an event published to a topic. Services that need the data subscribe to the relevant topics. The broker handles delivery, and services do not need to know about each other directly. This decoupling makes the system more resilient: if the price service goes down, the driver and ride services continue operating and publishing.

The two main types of real-time transports are:

* **Publish-subscribe (pubsub) systems** like Apache Kafka and Amazon Kinesis. Any service can publish to a topic, and any service can subscribe. Events have a retention period and can be replayed. This is ideal for event-driven architectures where multiple consumers need access to the same data stream.
* **Message queues** like RabbitMQ and Apache RocketMQ. Messages have intended recipients, and the queue ensures delivery to the right consumer. This is useful when specific tasks or commands need to be routed to specific worker services.

Apache Kafka deserves special attention because of its widespread adoption. Kafka stores events durably (on disk, replicated across nodes) and supports very high throughput. Think of Kafka as a persistent, distributed log where every event in your system is recorded and available for any service to consume.

## Batch Processing Versus Stream Processing

The mode of dataflow determines how data reaches a processing system. Once it arrives, the question is: how do you process it? The two paradigms are batch processing and stream processing.

### Batch Processing: Working with Historical Data

When data arrives in storage — databases, data lakes, or data warehouses — it becomes historical data. Processing this data in periodic jobs is called batch processing. You might run a job every hour to compute updated statistics, or every night to retrain an ML model on the latest data.


```
import pandas as pd
import numpy as np
from datetime import datetime, timedelta

# Simulating a batch processing job
np.random.seed(42)

# "Historical" ride data accumulated over a week
n_rides = 10_000
rides = pd.DataFrame({
    "ride_id": range(n_rides),
    "driver_id": np.random.randint(100, 200, n_rides),
    "fare": np.round(np.random.exponential(15, n_rides), 2),
    "distance_km": np.round(np.random.exponential(5, n_rides), 1),
    "city": np.random.choice(["Berlin", "Seoul", "Nairobi"], n_rides),
    "timestamp": [
        datetime(2025, 3, 10) + timedelta(minutes=np.random.randint(0, 7*24*60))
        for _ in range(n_rides)
    ],
})

# Batch job: compute daily statistics per city
rides["date"] = rides["timestamp"].dt.date
daily_stats = (
    rides.groupby(["city", "date"])
    .agg(
        total_rides=("ride_id", "count"),
        total_revenue=("fare", "sum"),
        avg_fare=("fare", "mean"),
        avg_distance=("distance_km", "mean"),
    )
    .round(2)
    .reset_index()
    .sort_values(["city", "date"]))

print("Daily batch statistics (first 10 rows):")
print(daily_stats.head(10).to_string(index=False))
```

Batch processing is well-suited for computations that do not need to be real-time: daily revenue reports, weekly model retraining, monthly cohort analysis. Features computed through batch processing are called **static features** or **batch features** because they change on the cadence of the batch job rather than in real time.

### Stream Processing: Working with Live Data

When data flows through a real-time transport like Kafka, it is streaming data. Processing this data as it arrives, rather than waiting for it to accumulate in a database, is stream processing.


```
from collections import defaultdict
from datetime import datetime

# Simulating stream processing of ride events
class StreamProcessor:
    """Maintains running statistics from a stream of events."""
    def __init__(self):
        self.counts = defaultdict(int)
        self.revenue = defaultdict(float)
        self.window_events = []

    def process_event(self, event):
        """Process a single ride event as it arrives."""
        city = event["city"]
        self.counts[city] += 1
        self.revenue[city] += event["fare"]
        self.window_events.append(event)

        # Keep only last 100 events for windowed statistics
        if len(self.window_events) > 100:
            self.window_events = self.window_events[-100:]

    def get_current_stats(self):
        """Return current aggregate statistics."""
        stats = {}
        for city in self.counts:
            stats[city] = {
                "total_rides": self.counts[city],
                "total_revenue": round(self.revenue[city], 2),
                "avg_fare": round(self.revenue[city] / self.counts[city], 2),
            }
        return stats

    def get_window_stats(self):
        """Return statistics for the last 100 events."""
        if not self.window_events:
            return {}
        recent = pd.DataFrame(self.window_events)
        return recent.groupby("city")["fare"].agg(["count", "mean"]).round(2).to_dict()

# Simulate a stream of events
processor = StreamProcessor()

for i in range(500):
    event = {
        "ride_id": i,
        "city": np.random.choice(["Berlin", "Seoul", "Nairobi"]),
        "fare": round(np.random.exponential(15), 2),
        "timestamp": datetime.now().isoformat(),
    }
    processor.process_event(event)

print("Running totals after 500 events:")
for city, stats in processor.get_current_stats().items():
    print(f"  {city}: {stats['total_rides']} rides, "
          f"${stats['total_revenue']} revenue, "
          f"avg fare ${stats['avg_fare']}")
```

Stream processing gives you low latency because you process data as soon as it is generated, without waiting for it to land in a database. Features computed from streams are called **dynamic features** or **streaming features** because they reflect the current state of the system.

The power of stream processing is in stateful computation. Consider computing user engagement windows. Instead of running a heavy daily query over a 30-day window, a stream processor maintains a running state and updates it incrementally as each new event arrives, computing only the delta.

### Combining Batch and Stream

Most real ML systems need both batch and stream features. A ride pricing model might use:

* **Batch features (computed daily):** driver lifetime rating, historical average fare by area, driver's typical working hours. These change slowly.
* **Streaming features (computed in real time):** number of available drivers right now, number of ride requests in the last 5 minutes, current surge multiplier. These change rapidly.


```
# Conceptual: combining batch and stream features for prediction
batch_features = {
    "driver_rating": 4.7,
    "area_avg_fare": 18.50,
    "historical_demand_ratio": 1.3,
}

streaming_features = {
    "current_available_drivers": 12,
    "requests_last_5min": 25,
    "current_surge": 1.8,
}

# Combine for prediction
all_features = {**batch_features, **streaming_features}

print("Combined feature vector for prediction:")
for k, v in all_features.items():
    source = "batch" if k in batch_features else "stream"
    print(f"  [{source:6s}] {k}: {v}")
```

The infrastructure to support this combination requires a batch processing pipeline for historical data and a stream processing pipeline for real-time data, plus a serving layer that merges both feature types at prediction time. This is one of the most challenging aspects of production ML systems.

### Batch vs Stream: A Summary

| Property | Batch Processing | Stream Processing |
| --- | --- | --- |
| **Data type** | Historical (at rest) | Streaming (in motion) |
| **Latency** | Minutes to hours | Milliseconds to seconds |
| **Processing trigger** | Periodic (scheduled) | Continuous (event-driven) |
| **Typical Tools** | Spark, MapReduce, pandas | Kafka Streams, Apache Flink |
| **Feature type** | Static / batch features | Dynamic / streaming features |
| **Best for** | Heavy aggregations, model training | Real-time serving, live monitoring |

An important theoretical observation: **batch processing is a special case of stream processing.** If you have a stream processor, you can process historical data by replaying it through the stream engine. The reverse is not true — you cannot easily make a batch processor handle real-time data. This is why modern tools like Apache Flink are designed as stream-first processors that also handle batch workloads.

## Putting It All Together: A Data Pipeline in Context

Let's trace how data flows through a complete system, from source to model prediction:

```
1. User requests a ride (user input data)
       ↓
2. Request event published to Kafka (real-time transport)
       ↓
3. Stream processor computes real-time features (available drivers, demand in last 5 min)
       ↓
4. Feature store merges stream features with batch features (driver rating, historical patterns - updated nightly via ETL)
       ↓
5. Prediction service uses combined features to compute price
       ↓
6. Price returned to user (< 100ms total)
       ↓
7. All events and predictions logged to data lake
       ↓
8. Nightly batch ETL processes logs ──→ updates analytical tables
       ↓
9. Weekly batch job retrains model using updated analytical data

```

Every concept from this lesson appears in this flow: ETL processes raw logs into analytical tables (step 8), services communicate via requests (step 5), real-time transports carry events between components (step 2), and both batch and stream processing contribute features (steps 3-4).

## Summary

This lesson covered the architectural foundations of data movement in production systems.

* **ETL (Extract, Transform, Load)** is the fundamental workflow for processing data from sources to analytical destinations. Extraction includes validation to catch problems early. Transformation handles cleaning, joining, and feature derivation. Loading writes the results to their target store. The ELT variant loads raw data first and transforms it later, trading early structure for faster ingestion.
* **Three modes of dataflow** connect processes in production. Data passing through databases is the simplest but slowest mode. Data passing through services (REST/RPC) is the most common for application logic and follows the microservice architecture pattern. Data passing through real-time transports (Kafka, Kinesis) uses a broker to decouple producers and consumers, enabling event-driven architectures that scale smoothly.
* **Batch processing** operates on historical data in periodic jobs, producing static features for ML models. **Stream processing** operates on live data as it arrives, producing dynamic features that reflect the current system state. Most production ML systems need both to feed models accurately at prediction time.

The key insight is that data pipelines are the backbone of ML systems. The model gets the attention, but the pipeline that delivers data to the model determines whether the system actually works in production. Understanding ETL, dataflow modes, and processing paradigms gives you the foundation to build reliable, maintainable data systems.
