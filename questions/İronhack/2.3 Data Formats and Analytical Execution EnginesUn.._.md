## Parquet: A Columnar Format in Depth

You already know that Parquet is a binary, column-major file format. But Parquet is much more than "columns stored together." Understanding its internal structure helps you write faster queries and make better choices about how you organize your data files.

### How Parquet Files Are Organized

A Parquet file is divided into row groups, and within each row group, data is stored by column chunks. At the end of the file, a footer contains metadata about the schema, the location of each column chunk, and statistics (min, max, null count) for each chunk.

```
Parquet File Layout:
┌─────────────────────────┐
│  Row Group 1            │
│  ├── Column 0 chunk     │
│  ├── Column 1 chunk     │
│  └── Column 2 chunk     │
├─────────────────────────┤
│  Row Group 2            │
│  ├── Column 0 chunk     │
│  ├── Column 1 chunk     │
│  └── Column 2 chunk     │
├─────────────────────────┤
│  Footer (metadata)      │
│  ├── Schema             │
│  ├── Row group offsets  │
│  └── Column statistics  │
└─────────────────────────┘

```

This structure enables several important optimizations. Because each column chunk is stored independently, a query that only needs three columns out of fifty can skip the other forty-seven entirely. Because the footer contains statistics for each column chunk, a query filtering on a specific value can skip entire row groups whose min/max range does not include that value. These optimizations happen at the file level, before any data is loaded into memory.

### Creating and Inspecting Parquet Files

Let's create a Parquet file and examine its metadata:


```
import pandas as pd
import numpy as np
import pyarrow as pa
import pyarrow.parquet as pq

# Create a dataset
np.random.seed(42)
n = 100_000
df = pd.DataFrame({
    "user_id": np.arange(n),
    "age": np.random.randint(18, 70, n),
    "score": np.random.uniform(0, 100, n),
    "city": np.random.choice(["Berlin", "Seoul", "Nairobi", "Toronto", "Lima"], n),
    "active": np.random.choice([True, False], n),
})

# Write to Parquet
df.to_parquet("users.parquet", index=False)

# Inspect metadata
parquet_file = pq.ParquetFile("users.parquet")
print(f"Number of row groups: {parquet_file.metadata.num_row_groups}")
print(f"Number of columns: {parquet_file.metadata.num_columns}")
print(f"Number of rows: {parquet_file.metadata.num_rows}")
print(f"\nSchema:")
print(parquet_file.schema_arrow)
```

The metadata tells you exactly how the file is structured without reading any data. This is a key advantage of Parquet over formats like CSV, where you have to scan the entire file to know basic facts like how many rows it contains.

### Column-Level Statistics and Pruning

Parquet stores statistics for each column chunk within each row group. These statistics enable predicate pushdown at the file level:


```
# Read metadata for the first row group
row_group = parquet_file.metadata.row_group(0)
for i in range(row_group.num_columns):
    col = row_group.column(i)
    print(f"Column: {col.path_in_schema:10s} | "
          f"Type: {col.physical_type:8s} | "
          f"Compressed size: {col.total_compressed_size:>8d} bytes")
```

When you filter a Parquet file — for example, `WHERE age > 60` — the reading engine can check the min/max statistics of the age column in each row group. If a row group's maximum age is 55, the entire row group is skipped without reading any of its data. This is called **row group pruning**, and it can dramatically reduce the amount of data that actually needs to be loaded.

### Selective Column Reading

One of Parquet's most practical advantages is the ability to read only the columns you need:


```
# Read only two columns from a five-column file
subset = pd.read_parquet("users.parquet", columns=["user_id", "city"])
print(f"Read {len(subset)} rows, {len(subset.columns)} columns")
print(subset.head())
```

With CSV, reading two columns out of five still requires parsing the entire file because columns are not stored independently. With Parquet, the engine skips directly to the column chunks it needs. For wide datasets with dozens or hundreds of columns, this difference translates to dramatic performance improvements.

## Apache Arrow: The In-Memory Standard

Parquet defines how columnar data is stored on disk. Apache Arrow defines how columnar data is represented in memory. Together, they form a powerful pair: Parquet for persistent storage, Arrow for in-memory computation.

### Why Arrow Matters

Before Arrow, every data tool had its own in-memory format. pandas used one representation, Spark used another, R used yet another. When data moved between tools, it had to be serialized and deserialized, which was slow and memory-intensive.

Arrow provides a standardized columnar memory format that multiple tools can share. When a Parquet file is read into Arrow memory, it is already in a format that pandas, DuckDB, Polars, and other tools can use directly — often with zero-copy access, meaning the data does not need to be duplicated.


```
import pyarrow as pa
import pyarrow.parquet as pq

# Read Parquet directly into Arrow table (zero-copy friendly)
arrow_table = pq.read_table("users.parquet")
print(f"Type: {type(arrow_table)}")
print(f"Rows: {arrow_table.num_rows}, Columns: {arrow_table.num_columns}")
print(f"\nColumn names: {arrow_table.column_names}")
print(f"\nFirst column (user_id), first 5 values: {arrow_table.column('user_id').to_pylist()[:5]}")
```

### Arrow to pandas and Back

Arrow integrates seamlessly with pandas. Converting between the two is fast because Arrow's columnar layout maps naturally to how pandas stores data internally:


```
# Arrow table → pandas DataFrame
df_from_arrow = arrow_table.to_pandas()
print(f"pandas DataFrame shape: {df_from_arrow.shape}")
print(df_from_arrow.dtypes)

# pandas DataFrame → Arrow table
arrow_from_df = pa.Table.from_pandas(df_from_arrow)
print(f"\nBack to Arrow: {arrow_from_df.num_rows} rows, {arrow_from_df.num_columns} columns")
```

Modern versions of pandas (2.0+) can use Arrow-backed data types natively, which improves memory efficiency and interoperability:


```
# Read Parquet using Arrow-backed dtypes in pandas
df_arrow_backed = pd.read_parquet("users.parquet", dtype_backend="pyarrow")
print(df_arrow_backed.dtypes)
```

Notice that the dtypes show Arrow types (like `int64[pyarrow]` and `string[pyarrow]`) instead of traditional NumPy-backed types. This is significant because Arrow string handling is more efficient than pandas' default object dtype for strings, and it provides better null handling through native support for missing values.

## DataFrames as Analytical Query Engines

When you write `df.groupby("city")["score"].mean()` in pandas, you are not just "manipulating data." You are executing an analytical query. The DataFrame is functioning as a query engine: it takes a description of what you want, builds an execution plan, and runs it. Understanding how this execution works helps you write faster, more efficient analysis code.

### Eager Execution: pandas

pandas uses **eager execution**: every operation is executed immediately and produces a result as soon as you call it. There is no planning phase; each line of code runs in the order you write it.


```
import pandas as pd

df = pd.read_parquet("users.parquet")

# Each line executes immediately
filtered = df[df["age"] > 30]           # Executes now: scans all rows
selected = filtered[["city", "score"]]   # Executes now: copies two columns
result = selected.groupby("city")["score"].mean()  # Executes now: groups and aggregates
print(result)
```

The advantage of eager execution is simplicity and predictability. You can inspect intermediate results at each step, which makes debugging straightforward. The disadvantage is that the engine has no opportunity to optimize across steps. In the example above, pandas first creates a filtered copy of the entire DataFrame, then creates another copy with only two columns, and finally groups and aggregates. Each step allocates memory and does work that might have been avoided with a smarter plan.

### Lazy Execution: A Smarter Approach

**Lazy execution** takes a different strategy. Instead of running each operation immediately, the engine builds a plan of all the operations you want to perform. It then analyzes the complete plan and finds an optimized way to execute it.

Tools like Polars and DuckDB use lazy execution. Let's see how DuckDB handles the same query:


```
import duckdb

# DuckDB can query pandas DataFrames directly
result = duckdb.sql("""
    SELECT city, AVG(score) as avg_score
    FROM df
    WHERE age > 30
    GROUP BY city
    ORDER BY avg_score DESC
""").df()

print(result)
```

Behind the scenes, DuckDB does not execute each clause independently. It builds a query plan that combines the filter, column selection, grouping, and aggregation into a single optimized pass over the data. The filter `WHERE age > 30` is pushed down to happen before any other processing, so rows that do not qualify are discarded as early as possible.

### Vectorized Execution

Both modern pandas operations and DuckDB use a technique called **vectorized execution**. Instead of processing one row at a time (which is what a Python for loop does), vectorized engines process entire columns or column chunks at once using optimized low-level routines.

Let's see the performance difference:


```
import numpy as np
import pandas as pd

n = 1_000_000
data = pd.DataFrame({
    "value": np.random.randn(n),
    "threshold": np.random.uniform(-1, 1, n),
})

# Approach 1: Row-by-row (Python loop) - SLOW
def row_by_row(df):
    results = []
    for _, row in df.iterrows():
        if row["value"] > row["threshold"]:
            results.append(row["value"] ** 2)
        else:
            results.append(0.0)
    return results

# Approach 2: Vectorized (column operations) - FAST
def vectorized(df):
    mask = df["value"] > df["threshold"]
    result = np.where(mask, df["value"] ** 2, 0.0)
    return result

# Time them (run only the vectorized version for the timing demo)
%time vec_result = vectorized(data)
print(f"Vectorized result shape: {vec_result.shape}")
```

The vectorized approach processes the entire column at once using NumPy's C-level routines, which operate on contiguous memory without Python interpreter overhead. This is typically 100x to 1000x faster than the row-by-row approach for large datasets.

The key insight is that vectorized execution works because of the column-major memory layout. When a column is stored contiguously, the CPU can load chunks of it into cache and process them sequentially. This hardware-level efficiency is what makes column-major formats and vectorized engines so powerful for analytics.

## Predicate Pushdown: Doing Less Work

**Predicate pushdown** is an optimization where filter conditions are applied as early as possible in the query execution pipeline, ideally at the storage level before data is even loaded into memory.

### Pushdown on Parquet Files

When reading a Parquet file with a filter, a smart engine uses the column statistics in the file's metadata to skip entire row groups:


```
import pyarrow.parquet as pq

# Read with a filter pushed down to Parquet
table = pq.read_table(
    "users.parquet",
    filters=[("age", ">", 60)],
    columns=["user_id", "age", "city"]
)

print(f"Rows after pushdown filter: {table.num_rows}")
print(table.to_pandas().head())
```

Without pushdown, the engine would read the entire file into memory and then apply the filter. With pushdown, row groups whose age column has a maximum value below 60 are never read at all. For large files with many row groups, this can reduce I/O by an order of magnitude.

### Pushdown in DuckDB

DuckDB takes pushdown further by integrating it into its query optimizer:


```
import duckdb

# DuckDB pushes predicates directly into Parquet scanning
result = duckdb.sql("""
    SELECT city, COUNT(*) as count, AVG(score) as avg_score
    FROM 'users.parquet'
    WHERE age > 60 AND active = true
    GROUP BY city
    ORDER BY count DESC
""").df()

print(result)
```

DuckDB's query planner pushes both the `age > 60` and `active = true` filters down to the Parquet reader, combines them with column projection (only reading the columns needed), and then performs the grouping and aggregation. The entire query executes without ever loading the full dataset into memory.

You can inspect DuckDB's query plan to see these optimizations:


```
# Show the query plan
plan = duckdb.sql("""
    EXPLAIN SELECT city, COUNT(*) as count, AVG(score) as avg_score
    FROM 'users.parquet'
    WHERE age > 60 AND active = true
    GROUP BY city
""")
print(plan)
```

The plan will show a `PARQUET_SCAN` operator with filters and projections pushed down, followed by the hash group-by aggregation. Reading query plans is a valuable skill for understanding and debugging performance.

## DuckDB: A Local Analytical Database

DuckDB is an embedded analytical database designed for fast, local-first analytics. Think of it as SQLite for analytical workloads: it runs inside your process, requires no server setup, and can query data directly from Parquet files, CSV files, and even pandas DataFrames.

### Why DuckDB Changes the Game

Traditional analytical databases (like Redshift or BigQuery) require network round-trips and cloud infrastructure. DuckDB runs on your laptop and can process surprisingly large datasets efficiently. This makes it ideal for exploratory analysis, feature engineering, and pipeline development before you scale to cloud infrastructure.


```
import duckdb

# DuckDB can query files directly without loading them first
result = duckdb.sql("""
    SELECT
        city,
        COUNT(*) as total_users,
        AVG(age) as avg_age,
        AVG(score) as avg_score,
        SUM(CASE WHEN active THEN 1 ELSE 0 END) as active_users,
        ROUND(SUM(CASE WHEN active THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) as active_pct
    FROM 'users.parquet'
    GROUP BY city
    ORDER BY total_users DESC
""").df()

print(result.to_string(index=False))
```

This query runs entirely in-process, using DuckDB's columnar execution engine with vectorized processing. It reads only the columns it needs from the Parquet file, applies predicate pushdown, and produces the result without creating a full in-memory copy of the dataset.

### DuckDB with pandas DataFrames

One of DuckDB's most practical features is its ability to query pandas DataFrames directly using SQL:


```
import pandas as pd
import duckdb

# Create a pandas DataFrame
orders = pd.DataFrame({
    "order_id": range(1, 1001),
    "customer_id": [f"C{i % 50:03d}" for i in range(1000)],
    "amount": [round(10 + 90 * (i % 7) / 6, 2) for i in range(1000)],
    "category": ["electronics", "books", "clothing", "food", "electronics",
                 "books", "clothing"] * 142 + ["food"] * 6,
})

# Query the DataFrame with SQL
top_customers = duckdb.sql("""
    SELECT
        customer_id,
        COUNT(*) as order_count,
        ROUND(SUM(amount), 2) as total_spent,
        ROUND(AVG(amount), 2) as avg_order
    FROM orders
    GROUP BY customer_id
    HAVING COUNT(*) > 15
    ORDER BY total_spent DESC
    LIMIT 10
""").df()

print(top_customers)
```

This lets you use SQL for complex aggregations while keeping your data in pandas for the rest of your workflow. There is no data copying — DuckDB reads the DataFrame's Arrow-compatible memory layout directly.

### Comparing pandas and DuckDB on the Same Query

Let's do a side-by-side comparison of the same analytical query in both pandas and DuckDB:


```
import pandas as pd
import numpy as np
import duckdb

# Larger dataset for meaningful comparison
np.random.seed(42)
n = 500_000
df = pd.DataFrame({
    "customer_id": np.random.randint(1, 10001, n),
    "product_category": np.random.choice(
        ["electronics", "clothing", "food", "books", "home", "sports"], n
    ),
    "amount": np.round(np.random.exponential(50, n), 2),
    "region": np.random.choice(["north", "south", "east", "west"], n),
})

# pandas approach
pandas_result = (
    df.groupby(["region", "product_category"])
    .agg(
        total_revenue=("amount", "sum"),
        avg_order=("amount", "mean"),
        order_count=("amount", "count"),
    )
    .reset_index()
    .sort_values("total_revenue", ascending=False)
    .head(10)
)

# DuckDB approach
duckdb_result = duckdb.sql("""
    SELECT
        region,
        product_category,
        ROUND(SUM(amount), 2) as total_revenue,
        ROUND(AVG(amount), 2) as avg_order,
        COUNT(*) as order_count
    FROM df
    GROUP BY region, product_category
    ORDER BY total_revenue DESC
    LIMIT 10
""").df()

print("pandas result:")
print(pandas_result.to_string(index=False))
print("\nDuckDB result:")
print(duckdb_result.to_string(index=False))
```

Both produce the same answer. For this dataset size, both will complete quickly. The differences become more visible at larger scale (millions of rows) and with more complex queries involving multiple joins, window functions, and subqueries, where DuckDB's query optimizer has more opportunities to outperform pandas' step-by-step approach.

## Eager vs Lazy: A Practical Framework

Now that you have seen both approaches in action, let's formalize when to use each:

* **Use eager execution (pandas)** when you are doing exploratory data analysis and want to inspect intermediate results, when your dataset fits comfortably in memory, when you need the rich ecosystem of pandas integrations (plotting, specialized accessors, sklearn interop), and when your operations are relatively simple (filters, column transformations, basic groupby).
* **Use lazy/SQL execution (DuckDB, Polars)** when you are running complex analytical queries with multiple aggregations, joins, or window functions, when your data is stored in Parquet files and you want to benefit from predicate pushdown and column pruning, when your dataset is large enough that memory efficiency matters, and when you want the query optimizer to find the best execution plan automatically.

In practice, the most effective workflow combines both. Use pandas for quick exploration and data manipulation, and switch to DuckDB or SQL when you need analytical horsepower:


```
import pandas as pd
import duckdb

# Step 1: Quick exploration in pandas
df = pd.read_parquet("users.parquet")
print(df.describe())
print(df["city"].value_counts())

# Step 2: Complex analytics in DuckDB
analysis = duckdb.sql("""
    WITH age_groups AS (
        SELECT *,
            CASE
                WHEN age < 25 THEN '18-24'
                WHEN age < 35 THEN '25-34'
                WHEN age < 45 THEN '35-44'
                WHEN age < 55 THEN '45-54'
                ELSE '55+'
            END as age_group
        FROM df
    )
    SELECT
        city,
        age_group,
        COUNT(*) as users,
        ROUND(AVG(score), 1) as avg_score,
        ROUND(SUM(CASE WHEN active THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) as active_pct
    FROM age_groups
    GROUP BY city, age_group
    ORDER BY city, age_group
""").df()

print(analysis)
```

This workflow gives you the interactivity of pandas for exploration and the optimization of DuckDB for heavy analytics, all within the same notebook.

## The Modern Analytics Stack on Your Laptop

Let's step back and see how the pieces fit together. The modern local analytics workflow looks like this:

* **Storage layer:** Parquet files on disk (or cloud storage). Column-major, compressed, with rich metadata and statistics.
* **Memory layer:** Apache Arrow provides a standardized in-memory columnar format. Data moves between tools without serialization overhead.
* **Execution layer:** Your choice of engine — pandas for interactive exploration, DuckDB for SQL analytics, Polars for high-performance DataFrame operations. All of them can read Parquet natively and many share Arrow memory.
* **Query optimization:** DuckDB (and Polars) provide query planners that optimize execution automatically, including predicate pushdown, column pruning, and join ordering.

This stack lets you do work on your laptop that used to require a data warehouse. For datasets up to tens of gigabytes — which covers most feature engineering, exploratory analysis, and pipeline development tasks — this local-first approach is faster (no network latency), cheaper (no cloud compute bills), and more interactive than a remote warehouse.

The mental model to carry forward is this: format, memory layout, and execution strategy are not separate concerns. Parquet's columnar layout enables Arrow's zero-copy reads, which enable DuckDB's vectorized execution, which enables predicate pushdown back into Parquet. Each layer builds on the one below it. Understanding this stack from top to bottom is what separates productive data engineers from those who wonder why their queries are slow.

## Summary

This lesson connected the abstract concepts of data formats and storage from earlier lessons to the concrete tools you use in practice.

* **Parquet** is more than a columnar file format. Its internal structure of row groups, column chunks, and metadata statistics enables powerful optimizations like selective column reading and row group pruning. Understanding this structure helps you write faster queries and organize your data files effectively.
* **Apache Arrow** provides a standardized in-memory columnar format that enables efficient data sharing between tools. It eliminates the serialization overhead that used to make tool interoperability expensive.
* **DataFrames are analytical query engines**, not just data containers. pandas uses eager execution (immediate evaluation), while DuckDB and Polars use lazy execution with query optimization. Each approach has strengths for different stages of analysis work.
* **Vectorized execution** processes entire columns at once using optimized native code, achieving orders-of-magnitude speedups over row-by-row Python loops. This performance comes directly from the column-major memory layout.
* **Predicate pushdown** applies filters as early as possible — ideally at the Parquet file level — to avoid loading data that will be discarded. DuckDB integrates this optimization into its query planner automatically.
* **DuckDB** brings warehouse-grade analytical performance to your laptop by combining columnar execution, query optimization, Parquet integration, and zero-copy access to pandas DataFrames. It is a practical tool for feature engineering, exploratory analysis, and pipeline development.
