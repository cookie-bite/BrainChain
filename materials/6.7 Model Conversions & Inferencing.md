# Model Conversions & Inferencing

## Introduction

Welcome to the last lesson of Unit 6. So far we've focused on the training side of deep learning — how to design networks, optimise them, regularise them, and adapt them to new tasks. Today we close the loop with the deployment side: once you have a trained model, how do you actually run it in production?

Training and inference look superficially similar — both involve a forward pass — but they have very different requirements. Training cares about gradient computation, mixed precision tricks, large batches, and sometimes hours-to-days of compute. Inference cares about latency, throughput, memory footprint, and portability to the device where the prediction needs to happen — which might be a server, a browser, a phone, an edge sensor, or a robot.

Today we cover the practical toolkit that bridges training to deployment:

* Model export formats: ONNX, TorchScript, TensorFlow SavedModel, TFLite, CoreML
* Inference runtimes: ONNX Runtime, TensorRT, OpenVINO
* Optimisation techniques: quantisation (post-training and QAT), pruning, knowledge distillation
* Inference engineering: batching, latency vs throughput trade-offs
* Hardware targets: CPU, GPU, edge accelerators, mobile

This lesson is a survey rather than a deep dive on any single tool — but every concept here will reappear in Unit 7 (MLOps & Deployment) and is directly applied in Friday's assessment, where you'll convert your cat-detection model and build the inference pipeline.

## Why Inference Is Different

It's worth slowing down here. The gap between "I trained a model in PyTorch" and "I can serve this model to users" is bigger than most beginners expect. The reasons are concrete:

* **Latency budgets** — a real-time camera app might give you 50ms per frame. Your trained PyTorch model might take 200ms.
* **Memory** — your training rig has 32GB of GPU RAM. Your phone has 4GB total.
* **Power** — a battery-powered device cares deeply about the joules per inference.
* **Portability** — your model trained in Python might need to run inside an iOS app, a browser via WebAssembly, or a C++ binary.
* **Reliability** — production systems need predictable, deterministic execution; training is stochastic by design.

The techniques in this lesson exist because of these gaps. They convert a "research model" into a "deployable artefact".

## Model Export Formats

A trained PyTorch model is a Python object. To deploy it, you usually need to export it into a more portable format. The main options:

### TorchScript

PyTorch's native serialisation. TorchScript captures your model's architecture and weights into a single file that can be loaded by C++ runtimes or by Python without the original class definition.


```
model.eval()
example = torch.randn(1, 3, 224, 224)
scripted = torch.jit.trace(model, example)
scripted.save("cat_detector.pt")
```

There are two flavours: **tracing** (`torch.jit.trace`) which records operations during a sample forward pass, and **scripting** (`torch.jit.script`) which compiles the whole `nn.Module` directly. Tracing is simpler but doesn't handle data-dependent control flow; scripting is more flexible but stricter about Python features.

TorchScript is the right choice when you stay in the PyTorch ecosystem. The C++ `libtorch` library can load it directly.

### ONNX (Open Neural Network Exchange)

ONNX is an open, framework-agnostic model format. Almost every framework (PyTorch, TensorFlow, Keras, JAX, MXNet) can export to ONNX, and many runtimes can execute it (ONNX Runtime, TensorRT, OpenVINO, …). It's become the lingua franca for cross-platform model deployment.


```
import torch.onnx
model.eval()
example = torch.randn(1, 3, 224, 224)

torch.onnx.export(
    model,
    example,
    "cat_detector.onnx",
    input_names=["input"],
    output_names=["logits"],
    dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
    opset_version=17,
)
```

The `dynamic_axes` parameter is crucial in production — it lets the exported model accept variable batch sizes (and sometimes variable input dimensions) instead of being locked to whatever the trace example used.

### TensorFlow SavedModel and TFLite

In the TensorFlow ecosystem, `SavedModel` is the standard server-side format and `TFLite` is the optimised mobile/edge format. If you trained in PyTorch, you can convert via ONNX as an intermediate format.

### CoreML (Apple)

Apple devices use CoreML. The `coremltools` library converts PyTorch and ONNX models to CoreML, after which they run efficiently on iPhones and Macs using the Neural Engine.

### Quick Comparison

| Format | Best for | Frameworks | Runtimes |
| --- | --- | --- | --- |
| **TorchScript (.pt)** | PyTorch-native deployment | PyTorch | `libtorch`, PyTorch |
| **ONNX (.onnx)** | Cross-platform deployment | Almost all | ONNX Runtime, TensorRT, OpenVINO, … |
| **SavedModel** | TensorFlow server-side | TensorFlow | TF-Serving |
| **TFLite (.tflite)** | Mobile / embedded | TensorFlow | TFLite runtime |
| **CoreML (.mlmodel)** | Apple devices | (via conversion) | CoreML |

For Friday's assessment, **ONNX** is the recommended format — it's portable, widely supported, and simple to inspect with tools like Netron.

## Inference Runtimes

A format is just a file. To run it, you need a runtime — the engine that loads the model and executes its operations on actual hardware.

### ONNX Runtime

Microsoft's flagship inference engine. Runs ONNX models efficiently on CPU, GPU (CUDA, DirectML), and various accelerators. It's the most common starting point for production deployment in 2026.


```
import onnxruntime as ort
import numpy as np

session = ort.InferenceSession("cat_detector.onnx")
inputs = {"input": np.random.randn(1, 3, 224, 224).astype(np.float32)}
outputs = session.run(None, inputs)
print(outputs[0].shape)
```

That's it. Three lines for inference, and the model is now a deployable artefact independent of PyTorch.

### TensorRT (NVIDIA)

NVIDIA's GPU-specific runtime. Aggressively optimises ONNX models for NVIDIA GPUs using fused kernels, lower-precision compute, and other tricks. Often gives 2–10× speedup over ONNX Runtime + CUDA on the same hardware. Used in self-driving cars, real-time video, and any latency-critical NVIDIA-GPU application.

### OpenVINO (Intel)

Intel's analogue for CPU and Intel-GPU inference. Excellent for x86 server deployment when you don't have a GPU, and standard for Intel-based edge devices (Movidius, Xe Graphics).

### Choosing a Runtime

| Target | Recommended runtime |
| --- | --- |
| Linux/Windows server, CPU | ONNX Runtime, OpenVINO |
| NVIDIA GPU server | TensorRT, ONNX Runtime + CUDA |
| Apple devices | CoreML |
| Android / generic mobile | TFLite, ONNX Runtime Mobile |
| Browser | ONNX Runtime Web (WASM/WebGPU) |
| Embedded edge | TFLite, OpenVINO, vendor SDKs |

For tomorrow's assessment we'll use **ONNX Runtime on CPU** — it works everywhere and lets you focus on the inference logic instead of hardware specifics.

## Quantisation: Smaller and Faster

Most deep learning models are trained in 32-bit floating point (FP32). For inference, you almost never need that much precision. Quantisation reduces numerical precision to gain speed and shrink memory.

The most common targets:

* **FP16** — half precision; 2× smaller and often 2× faster on modern hardware (GPUs, recent CPUs)
* **INT8** — 8-bit integers; 4× smaller, often 2–4× faster, with a small accuracy cost
* **INT4 / lower** — used for very large models (LLMs); aggressive compression, more accuracy risk

### Post-Training Quantisation (PTQ)

The simplest approach: train in FP32 as usual, then quantise the trained model. PyTorch and ONNX Runtime both support PTQ:


```
from onnxruntime.quantization import quantize_dynamic, QuantType

quantize_dynamic(
    model_input="cat_detector.onnx",
    model_output="cat_detector.int8.onnx",
    weight_type=QuantType.QInt8,
)
```

PTQ is essentially free — a few seconds of conversion — and on most CNNs you lose <1% accuracy.

### Quantisation-Aware Training (QAT)

If PTQ accuracy loss is unacceptable, QAT simulates quantisation effects during training so the model learns to compensate. More work, but gives near-FP32 accuracy at INT8 throughput. Common for production models with tight quality budgets.

> **When Quantisation Hurts:** Quantisation is mostly safe but can hurt accuracy when:
> * The model has very small weights (already close to the quantisation step)
> * Activations have extreme dynamic range
> * BatchNorm is folded incorrectly (quantisation tools usually fold BN into the preceding conv, but bugs happen)
>
>
> Always validate accuracy after quantisation by running the quantised model on your validation set. Trust nothing: quantisation is "cheap and free" until it isn't.

## Pruning

Pruning removes weights from the network — either individual ones (unstructured pruning) or whole channels/heads (structured pruning).

* **Unstructured pruning** zeroes out the smallest-magnitude weights. Storage shrinks if you use sparse formats; speed gains require hardware that exploits sparsity.
* **Structured pruning** removes whole filters or attention heads. Slower, smaller model — both with no special hardware needed. Common for production CNNs.

Quantisation is usually applied first and is more effective; pruning is a secondary tool used when more compression is needed.

## Knowledge Distillation

Train a small "student" model to mimic the outputs of a large "teacher" model. The student learns from both the original labels and the teacher's softmax probabilities (which contain richer "dark knowledge" than hard labels). Distillation often produces small models that beat training the same architecture from scratch on hard labels.

Distillation is a major tool in modern LLM compression — many of the "small chat models" you see (Phi, Gemma-mini, Llama-tiny) are distilled versions of much larger teachers.

## Building an Inference Pipeline

A real deployment is more than `model(x)`. The full pipeline typically includes:

1. **Pre-processing** — resize, normalise, convert format. Must match training-time pre-processing exactly.
2. **Tokenisation / encoding** — for text/audio inputs.
3. **Model forward pass** — the actual inference.
4. **Post-processing** — softmax, argmax, NMS for detection, decoding for sequences, threshold for binary.
5. **Output formatting** — JSON, image overlay, etc.

A common bug: students forget to apply the same normalisation at inference that they used during training. The model gets garbage inputs and produces garbage outputs. Always reuse the exact preprocessing transforms. A clean pattern:


```
def preprocess(pil_image):
    return val_transform(pil_image).unsqueeze(0).numpy().astype(np.float32)

def predict(pil_image):
    x = preprocess(pil_image)
    logits = session.run(None, {"input": x})[0]
    probs = softmax(logits, axis=1)
    return probs[0]
```

Wrap that in a small CLI or REST API and you have a deployable inference service.

## Latency vs Throughput

Two related but different metrics:

* **Latency** — time to process a single input (e.g., 50 ms per image)
* **Throughput** — number of inputs processed per unit time (e.g., 100 images per second)

You can usually trade one for the other. Larger batch sizes increase throughput (more efficient hardware utilisation) but also increase latency for any single request. For a real-time camera, you care about latency. For a batch processing job that classifies a million photos overnight, you care about throughput.

A practical lesson: profile your inference pipeline and find the bottleneck. Often it isn't the model forward pass — it's image loading, format conversion, or post-processing.


```
import time

start = time.perf_counter()
for _ in range(100):
    _ = session.run(None, inputs)
elapsed = (time.perf_counter() - start) / 100
print(f"Average inference latency: {elapsed * 1000:.1f} ms")
```

Three lines. Always run them. You'd be amazed how many production deployments don't.

## Hardware Targets

A quick survey of where models actually run in 2026:

* **Server CPU** — common for low-cost cloud inference. Optimise with INT8 quantisation + ONNX Runtime/OpenVINO.
* **Server GPU (NVIDIA)** — high throughput at scale. Use TensorRT for serious workloads.
* **Mobile (iOS / Android)** — TFLite or CoreML; INT8 quantisation almost always.
* **Edge devices** — sensors, drones, IoT. Usually small custom models with vendor-specific SDKs.
* **Browser** — ONNX Runtime Web (WASM or WebGPU); great for privacy-preserving inference.

For the cat-detection assessment, "server CPU + ONNX Runtime + INT8 quantisation" is a perfectly realistic deployment story.

## Summary

Today you learned how to bridge training and deployment:

* **Export formats** (ONNX, TorchScript, TFLite, CoreML) turn trained models into portable artefacts.
* **Inference runtimes** (ONNX Runtime, TensorRT, OpenVINO, …) execute these artefacts efficiently on specific hardware.
* **Quantisation** (PTQ and QAT) trades a small amount of accuracy for major gains in speed and memory; INT8 is the standard sweet spot for CNNs.
* **Pruning and knowledge distillation** are additional compression techniques used when more efficiency is needed.
* A real inference pipeline is `preprocess` $\rightarrow$ `forward pass` $\rightarrow$ `post-process`; the most common bugs are mismatches between training-time and inference-time preprocessing.
* Latency vs throughput is a deliberate trade-off you must measure for your use case.
* Choose the runtime for your target hardware: ONNX Runtime is a portable default; TensorRT for NVIDIA GPUs; CoreML for Apple; TFLite for mobile.
